# Intent Service (`intent-service/`)

> Intent truth: structured TS 28.312 intents addressed to a chosen intent handling function, their reports, and the rApp autonomy-dispatch hand-off that turns an inference outcome into an intent.

| | |
|---|---|
| Standards basis | 3GPP TS 28.312 (Intent NRM) |
| R1 route / port | `/intent-service` via R1 Termination (container :8000) |
| Depends on (over R1) | rApp Management (`GET /rapp-mgmt/instances/{id}`, autonomy dispatch only); outbound webhooks to RMIHs, report recipients and operator destinations |
| Called by | rApps via `sdk.intent`; GUI BFF (intents, autonomy dispatches); SA SMOS O1-CM handler (reads intents, publishes reports, registers as RMIH `sa-smos`, see [`../sa-smos/README.md`](../sa-smos/README.md)); SO SMOS identity may register as an RMIH |
| Database tables | `intent`, `intent_utility_formula`, `intent_report`, `intent_handling_function`, `autonomy_dispatch` |
| Unit tests | `tests/`, SQLite, standalone (counts: [docs/TEST_COUNTS.md](../docs/TEST_COUNTS.md)) |
| Status | Done. The 8 value datatypes are checked by structure (`SA-INTENT-partial`, closed); `GeoArea` is the one `ValueRangeType` alternative with a documented simplification (1.2) |

## 1. High-level design (HLD)

### 1.1 Purpose and scope

An rApp (the intent owner or RMIO) states what it wants as a TS 28.312 `Intent`: expectations over an object, with
targets, contexts, priority and report control. It addresses the intent to one `IntentHandlingFunction` (RMIH) it
discovered. Intent Service validates the intent, checks it against that RMIH's declared capabilities, stores it,
produces the initial reports, pushes it to the RMIH (and pushes again when its admin state changes and when it is
deleted) and delivers every later `IntentReport` to the recipients the intent named. It also owns `AutonomyDispatch`, the record that connects an AI/ML inference outcome to an intent
according to the rApp instance's autonomy mode. It does not enforce anything itself: enactment belongs to the RMIH.

### 1.2 Standards basis

Realises `../../specs/5G_APIs/TS28312_IntentNrm.yaml` plus the five expectation-family files
([5GC network](../../specs/5G_APIs/TS28312_5GCNetworkExpectation.yaml),
[edge service support](../../specs/5G_APIs/TS28312_EdgeServiceSupportExpectation.yaml),
[network maintenance](../../specs/5G_APIs/TS28312_NetworkMaintenanceExpectation.yaml),
[radio network](../../specs/5G_APIs/TS28312_RadioNetworkExpectation.yaml),
[radio service](../../specs/5G_APIs/TS28312_RadioServiceExpectation.yaml)).

| Realised | Where |
|---|---|
| `Intent` with its spec attributes, closed enums, `extra="forbid"` | `app/ts28312.py`, `CreateIntentRequest` |
| Every expectation checked against its family: a known specialised target or context name must use an allowed condition and a matching value; unspecialised names are valid as generic targets or contexts, as the spec's `oneOf` allows | `app/ts28312_families.py` (generated by `../scripts/generate_ts28312_families.py`; do not hand-edit) |
| `IntentHandlingFunction` with `intentHandlingCapabilityList`, `supportedNegotiationFunctionalities`, `supportedUtilityList` | `RegisterRmihRequest` |
| `IntentReport` of every kind: fulfilment, conflict, feasibility check, exploration, utility, fulfilment negotiation, decomposition | `IntentReportRequest` |
| `IntentUtilityFormula` IOC | `/intent-utility-formulas` |
| `IntentFulfilmentNegotiationFeedback` | `/intents/{id}/negotiation-feedback` |
| `IntentReportControl` report delivery | `_deliver_report` |

Value datatypes (`app/ts28312_datatypes.py`, SA-INTENT-partial): `Frequency`, `UEGroup` (with `PlmnId`, `Snssai`,
`QoSId`), `CivicArea` with `CivicAddress`, `ReportingCondition` = `TimeCondition` (a `SchedulingTime`:
`TimeWindow`, `timeIntervals`, `daysOfWeek` or `daysOfMonth`) or `TargetFulfilmentCondition`, are checked by
structure: required and exclusive keys (`QoSId`: exactly one of `qCI` / `fiveQI`; `CivicArea`: exactly one of
`civicAddress` / `locationLabel`), the TS 28.541 / 28.623 patterns and ranges (MCC, MNC, SST, SD, 5QI, days) and
unknown keys refused. `ValueRangeType` is enforced as a whole for every unspecialised target or context: a scalar,
a list of them, or one object matching a structured alternative (a `{"nCI": 101}`-style free object is refused). A
specialised name bound to a datatype (`UEGroup`, `CivicArea`, `DlFrequency`, `UlFrequency`, `schedulingTime`)
must carry that datatype. Specialised names with a family value schema (`Cell` and the like) keep that schema.

Not realised or deviating: DN-typed attributes carry plain strings (flat REST, no containment tree); `DateTime` and
`FullTime` strings are checked by their RFC 3339 shape, not calendar validity; `GeoArea` / `GeoCoordinate` check
the structure and the latitude / longitude ranges but not polygon closure.
`rmihId`, `rmioId` and `intentHandlingScope` on an intent, and `notificationDestination` on an RMIH, are this
build's own additions. 

### 1.3 Position in the platform

```
 rApp / GUI (RMIO) ──POST /intents {rmihId}──►  Intent Service ──webhook (new intent)──► RMIH (e.g. SA SMOS O1-CM handler)
                                                    ▲   │                                     │
```

### 1.5 Design decisions

**RMIH selection is consumer-side**, following TS 28.312 NRM containment (`IntentHandlingFunction` contains `Intent`):

- `POST /intents` requires `rmihId`: the caller addresses one RMIH it has discovered via
  `GET /intent-handling-functions`.
- The RMIH's declared capabilities and scope must cover the intent (`RMIH_CAPABILITY_MISMATCH`, 422): a capability
  for every expectation object type, the handling scope if one is declared, the negotiation functionality the
  `intentMgmtPurpose` needs (when the RMIH declares any), and, for a fulfilment purpose, every target named in the
  capability's `supportedExpectationTargetInfoList` (with the same condition where declared).
- An RMIH with intents addressed to it cannot be deregistered (409 `INTENT_HANDLING_FUNCTION_IN_USE`, call flow 09c), so no
  intent disappears under its owner; registering an `rmihId` again updates it in place and keeps its intents (it was a
  409, and SA SMOS deleted the handler first, which cascaded away every intent). `Intent.rmih_id` keeps its
  `ON DELETE CASCADE` foreign key.
- Dispatch is one notification to the named RMIH, an outbox row committed with the intent (`PR-MSG-1.9`). RMIHs register with a `notificationDestination`.
  The RMIH is also told of the intent's life after that (INTENT-LIFECYCLE-PUSH): an admin-state change that changes the state pushes
  `ADMIN_STATE_CHANGED`, and a delete of an existing intent pushes `INTENT_DELETED`, each an outbox row in the transaction of the change; the create push
  carries `event` `INTENT_CREATED`. A PATCH to the state the intent already has and a delete of an unknown id push nothing. Every push names the intent,
  its current `adminState`, its `expectationObjectTypes` and its `rmioId`, so a handler can act on a delete without reading the intent back (it is gone).
  A handler answers an `event` it does not know with 2xx and does nothing, so an event can be added without a release of every handler; a 4xx answer
  (SO SMOS has no handler route: 404) counts as delivered and is not retried.

**Autonomy dispatch.** An rApp instance carries `autonomyMode` (`AUTONOMOUS` / `ASSIST` / `SHADOW`, default
`SHADOW`) and `regionScope` (rApp Management). An inference outcome is handed to
`POST /intent-service/autonomy-dispatches`:

| Mode | Behaviour |
|---|---|
| `AUTONOMOUS` | An Intent is created at once, scoped to the instance's `regionScope`; status `DISPATCHED`. |
| `ASSIST` | `AWAITING_SCOPE` until the operator calls `/resolve` (with scope → Intent, `DISPATCHED`) or `/reject` (→ `REJECTED`; 409 unless `AWAITING_SCOPE`). |
| `SHADOW` | `SHADOWED`; never enforced, no Intent ever. |

Every mode notifies the operator (an outbox row committed with the dispatch, `smo_shared.outbox`); notification is not mode-gated. All modes
validate the RMIH and capability up front, so a SHADOW dispatch to an unknown or incapable RMIH is rejected too.
The mode is snapshotted onto the dispatch at request time and never rewritten by a later change on the instance.

**Other decisions**

- **Strict validation.** Every intent, expectation and report is validated against the spec models; no free-form
  intent bodies.
- **Feasibility and conflict are computed, not trusted.** A target is feasible when the RMIH's capability names it.
  An infeasible fulfilment intent is rejected; an infeasible `FEASIBILITYCHECK*` intent is accepted and carries the
  `INFEASIBLE` report. Target conflicts with other `ACTIVATED` intents (same object instance and target name,
  different condition or value) are reported as `TARGET_CONFLICT`, never rejected.
- **Initial report.** Creation writes an `IntentReport` (fulfilment `NOT_FULFILLED` / `RECEIVED`, plus
  conflict/feasibility when present) that becomes `intentReportReference`. Every later report replaces that
  reference.
- **Fulfilment and conflict summary (`GUI-9.8`).** Every report this module stores updates three columns of the
  intent (`_apply_report`): a fulfilment report sets `fulfilmentPercent` (the share of its targets that are
  `FULFILLED`; of its expectations when it lists no targets; 0 or 100 from the intent's own verdict when it lists
  neither; one decimal) and `fulfilled` (the intent's own `intentFulfilmentInfo.fulfilmentStatus`); a report that
  carries conflict reports sets `inConflict` (an empty list clears it; the conflicts found at creation count). They
  are columns, not computed from the JSON at read time, so `GET /intents?fulfilled=&in_conflict=` filters in SQL.
  Revision `0037` filled them for the intents that existed before; a report written by the previous release during
  a rolling upgrade does not update them until the next one.
- **Region scope bounds, never widens.** For an autonomy-created intent the region scope fills a missing
  `objectInstance` (a different one is rejected) and its `cells` become the expectation's `Cell` context; an
  expectation that already names cells is intersected with the region, and an empty intersection is rejected.
- **Notifications go through the transactional outbox** (`smo_shared.outbox`, `PR-MSG-1.9`). The pushes to the RMIH, report delivery and
  operator notification are rows in the same transaction as the intent, report or dispatch they announce, sent right after it commits (2 s
  timeout), at least once; they never fail the triggering call, and a crash after the commit no longer loses them. An autonomy dispatch and the
  Intent it creates are now one transaction (`_create_intent_row` no longer commits; its callers do). A destination is never guessed.
- **Security / RBAC** (call flow 09, DOC-CF-1.8; the caller's role and invoker id are the ones R1 Termination stamps).
  An rApp caller may not register or deregister an RMIH or publish a report (403 `ROLE_NOT_PERMITTED`), and an
  `rmihId` that parses as a UUID is refused for anyone (D-SEC-POLICY-1). An rApp's `rmioId` is its own invoker id, the
  caller is recorded as the intent's owner (`ownerInvokerId`), and only the owner rApp may change the admin state,
  answer a negotiation report or delete the intent (403 `INTENT_ACCESS_DENIED`); the console and modules act for others,
  but must name the intent's `rmioId` as `requesterId` to change its admin state. An rApp dispatches only for the instance
  whose `oauthClientId` is its invoker id (403 `INSTANCE_IDENTITY_MISMATCH`), recorded as `dispatchedBy`. Resolve and
  reject need the console's signed-in user (`X-R1-Acting-User`; 403 `ROLE_NOT_PERMITTED` for an rApp or a module on its own
  account), recorded as `resolvedBy` / `rejectedBy`. The GUI BFF pins `rmioId` for GUI-created intents and restricts
  registration, report publication and deletion to admin (`../gui-bff/app/rbac.py`). Reads are open to any caller.
- **Idempotency.** `DELETE` of an unknown intent, RMIH or formula is a 204 no-op (no push). Admin-state change to the current
  state creates no new report and pushes nothing. Neither route is `@idempotent`: a repeat is already a no-op.

### 2.2 Data model

`intent`

| Column | Notes |
|---|---|
| `intent_id` | UUID PK |
| `intent_expectations` | JSON list of validated expectations |
| `intent_mgmt_purpose` | One of `FEASIBILITYCHECK`, `FEASIBILITYCHECK_WITH_RECOMMENDATIONS`, `FULFILMENT_WITHOUT_NEGOTIATION` (default), `EXPLORATION`, `FULFILMENT_WITH_NEGOTIATION` |

| `intent_utility_formula_id` | FK `intent_utility_formula`, `ON DELETE SET NULL` |
| `fulfilment_percent`, `fulfilled`, `in_conflict` | Nullable summary of the newest fulfilment and conflict reports (1.5, `GUI-9.8`, revision `0037`) |

`intent_exploration_report`, `intent_utility_reports`, `intent_fulfilment_negotiation_report`,

`intent_utility_formula`: `intent_utility_formula_id` PK; `utility_function_id`; `utility_parameter_list`;

### 2.3 State machines

Intent admin state (`PATCH /intents/{id}/admin-state`, creator only)

| From | Event | To | Side effect |
|---|---|---|---|
| `ACTIVATED` | `newState = DEACTIVATED` | `DEACTIVATED` | New report: fulfilment `NOT_FULFILLED` / `SUSPENDED`, delivered per report control; `ADMIN_STATE_CHANGED` pushed to the RMIH |
| `DEACTIVATED` | `newState = ACTIVATED` | `ACTIVATED` | New report: `NOT_FULFILLED` / `RECEIVED`; `ADMIN_STATE_CHANGED` pushed to the RMIH |
| either | same state | unchanged | none |

Autonomy dispatch

| Mode at request | Initial status | Event | Next |
|---|---|---|---|
| `AUTONOMOUS` | `DISPATCHED` (Intent created in the same call) | none | terminal |
| `SHADOW` | `SHADOWED` | none | terminal |
| `ASSIST` | `AWAITING_SCOPE` | `resolve {regionScope}` | `DISPATCHED`, Intent created |
| `ASSIST` | `AWAITING_SCOPE` | `reject {rejectedBy, reason?}` | `REJECTED` |

`resolve` and `reject` from any status other than `AWAITING_SCOPE` are refused with 409
`AUTONOMY_DISPATCH_NOT_AWAITING_SCOPE`. `DISPATCHED`, `SHADOWED` and `REJECTED` are terminal.

| Method | Path | Purpose | Notable errors |
|---|---|---|---|
| POST | `/autonomy-dispatches` | Request a dispatch `{instanceId, modelId?, expectations[], priority, rmihId, intentMgmtPurpose, intentHandlingScope?, notificationDestination?, userLabel?}` (201) | 503 `ENDPOINT_UNREACHABLE` (rApp Management did not answer); 404 `RAPP_INSTANCE_NOT_FOUND`; 403 `INSTANCE_IDENTITY_MISMATCH` (an rApp, not the instance's `oauthClientId`); 404 `INTENT_HANDLING_FUNCTION_NOT_FOUND`; 422 `RMIH_CAPABILITY_MISMATCH`; 422 expectation schema; 422 `SCHEMA_VALIDATION_FAILED` when the region scope excludes the expectation |

| POST | `/autonomy-dispatches/{dispatch_id}/reject` | `{rejectedBy, reason?}` (`rejectedBy` is replaced by the console user) | 403 `ROLE_NOT_PERMITTED`; 404; 409 `AUTONOMY_DISPATCH_NOT_AWAITING_SCOPE` |
| GET | `/health` | Liveness probe | |

**Repeats (SDK-RETRY-IDEMPOTENCY).** `POST /intents`, `/intent-reports` and `/autonomy-dispatches` are `@idempotent("intent-service", status_code=201)`
(`smo_shared.idempotency`, PR-ST-3): a repeat with the same `Idempotency-Key` (every SDK POST carries one, and repeats it after a transport error,
502 or 504) is answered with the first answer and `Idempotent-Replayed: true`, and creates no second intent, report or dispatch and no second
notification. The same key with another body is 422 `IDEMPOTENCY_KEY_REUSED`; a repeat while the first still runs is 409
`IDEMPOTENCY_KEY_IN_PROGRESS`. `POST /intent-handling-functions` is not decorated: a repeat upserts the same row by `rmihId`. The other POSTs are not
called by the SDKs and are not decorated.

An intent created from a dispatch carries `rmioId = instanceId`, is owned by the rApp that dispatched, and has a report control with a 60 s observation period
and, when the dispatch has one, `reportRecipientAddress = notificationDestination`.

### 2.5 Interactions

| Trigger | Interaction | Failure behaviour |
|---|---|---|
| Intent created (any path) | POST to the RMIH's `notificationDestination`: `{intentId, event: "INTENT_CREATED", adminState, expectationObjectTypes, intentPriority, rmioId, intentMgmtPurpose}`. The RMIH reads the intent back over R1. | Outbox row, committed with the intent; unreachable RMIH never fails create |
| Admin state changed (not to the state it had) | POST to the RMIH's `notificationDestination`: `{intentId, event: "ADMIN_STATE_CHANGED", adminState, expectationObjectTypes, rmioId}` (INTENT-LIFECYCLE-PUSH) | Outbox row, committed with the change and its report |
| Intent deleted (an existing one) | POST to the RMIH's `notificationDestination`: `{intentId, event: "INTENT_DELETED", adminState, expectationObjectTypes, rmioId}`; the intent can no longer be read back | Outbox row, committed with the delete |
| Any report written (initial, admin-state, published) | For each `intentReportControl` with a `reportRecipientAddress` whose `expectedReportTypes` (all when empty) intersect the report: POST `{notificationType: "notifyIntentReport", ...report view}` | Outbox row, committed with the report |
| Autonomy dispatch | `GET /rapp-mgmt/instances/{id}` for `autonomyMode` and `regionScope` | No answer (connection error or timeout) → 503 `ENDPOINT_UNREACHABLE`; non-200 → 404 `RAPP_INSTANCE_NOT_FOUND` |
| Autonomy dispatch / resolve / reject | POST dispatch summary to `notificationDestination` | Outbox row, committed with the dispatch; none sent when no destination; non-http(s) schemes are refused by the SSRF guard (`smo_shared.webhook`) at enqueue and at send |

All notifications are sent through `smo_shared.webhook.post_webhook` (by the outbox), which blocks non-http(s) schemes and loopback,
link-local, multicast and reserved literal addresses. No background tasks.

### 2.7 Error codes

| Code | HTTP | When |
|---|---|---|
| `INTENT_NOT_FOUND` | 404 | Unknown intent id (read, admin-state, feedback, publish report) |
| `INTENT_HANDLING_FUNCTION_NOT_FOUND` | 404 | `rmihId` not registered (create intent, autonomy dispatch) |
| `RMIH_CAPABILITY_MISMATCH` | 422 | Object type, scope, negotiation functionality or fulfilment target not covered by the RMIH |
| `NRM_OBJECT_NOT_FOUND` | 404 | Unknown utility formula or report; no negotiation report to answer |
| `SCHEMA_VALIDATION_FAILED` | 422 | Report with no content; unknown outcome id; expectation outside the dispatch region scope |
| `SERVICE_NAME_CONFLICT` | 409 | An external (UUID) `rmihId` on RMIH registration |
| `ROLE_NOT_PERMITTED` | 403 | An rApp registering, deregistering an RMIH or publishing a report; resolve / reject by an rApp or without a console user |
| `INTENT_ACCESS_DENIED` | 403 | An rApp acting on an intent it does not own; a `requesterId` that is not the creator |
| `INSTANCE_IDENTITY_MISMATCH` | 403 | An rApp dispatching for an instance whose `oauthClientId` is not its invoker id |
| `INTENT_HANDLING_FUNCTION_IN_USE` | 409 | Deregistering an RMIH that intents are still addressed to |
| `RAPP_INSTANCE_NOT_FOUND` | 404 | Autonomy dispatch for an unknown instance |
| `ENDPOINT_UNREACHABLE` | 503 | Autonomy dispatch when rApp Management does not answer the instance lookup |
| `AUTONOMY_DISPATCH_NOT_FOUND` | 404 | Unknown dispatch id |
| `AUTONOMY_DISPATCH_NOT_AWAITING_SCOPE` | 409 | Resolve or reject outside `AWAITING_SCOPE` |
| `IDEMPOTENCY_KEY_REUSED` / `IDEMPOTENCY_KEY_IN_PROGRESS` / `IDEMPOTENCY_KEY_INVALID` | 422 / 409 / 422 | `Idempotency-Key` on a create route: used for another body, the first request still running, or not 1 to 255 printable characters (`smo_shared.idempotency`) |
| FastAPI validation (`HTTPValidationError`, 422) | 422 | Any body that fails the strict spec models (unknown field, bad enum, family-rule violation, empty required list) |

### 2.8 Limits and open items

- Value datatypes are structure-checked (1.2); a caller that sent a free-form object as a generic target or context value (the old SDK `schedulingTime` shape did) is now refused with 422.
- `ts28312_families.py` is generated from the spec text and carries its spelling as-is, including conditions such
  as `IS_less_THAN` (5GC `5GSession`) and `S_EQUAL_TO` (radio-service `AssuranceDuration`) that cannot equal any
  value of the `Condition` enum, so those two specialised contexts can never validate.
- A module may publish a report for any intent, not only those addressed to it: module invoker ids are not tied to an `rmihId`.
- `rApp Management` is the only cross-module read; the pushes to the RMIH are outbox rows, retried by the outbox sweep like every other notification.
- The ON DELETE CASCADE of a deregistered RMIH's autonomy dispatches is verified against PostgreSQL, not in the unit suite.

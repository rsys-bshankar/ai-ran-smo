# Working in this repo

This is the Phase 1 SMO reference implementation. The documentation:

- `README.md` — what it is, the modules, quickstart, layout;
- `<module>/README.md` — each module's HLD, LLD and unit tests (update it in the same change as the module's code);
- `docs/ARCHITECTURE.md` — layers, golden rules, R1 conventions, standards per service;
- `docs/RAPP_PACKAGING.md` — rApp CSAR layout and the manifest / capabilities parameters;
- `docs/configuration/` — every environment variable the code reads, one `<group>.md` per module (generated by `scripts/config_reference.py --write`) beside
  its `<group>.json` (the descriptions: a new `os.environ` read needs one in its module's file, or `tests_integration/test_config_reference.py` fails);
- `docs/test-counts/` — the number of test files, test functions and collected tests of each suite, one `<suite>.md` per suite and an index (generated by
  `scripts/count_tests.py --write`; the READMEs describe what each test file covers and link to their suite's file instead of stating a count, and CI
  fails when one is stale);
- `docs/STANDARDS.md` — frozen design decisions, standards compliance matrices, runtime realization;
- `docs/CODE_DOCUMENTATION.md` — the rule for the comments and docstrings inside the source files (a file description, a description of every function that needs one, a sentence on every test), and how CI holds it;
- `OPEN_ITEMS.md` — what is still open, and why; the converged rewrite's rows are `docs/plan/rows/S0.md` … `S8.md`, one file per stage;
- `CHANGELOG.md` and `docs/RELEASES.md` — what changed for an operator, and how releases are versioned and cut; a change an operator would notice adds a
  fragment `changelog.d/<id>.md`, which `scripts/changelog.py --write` assembles into `[Unreleased]` at release (a pull request never edits `CHANGELOG.md`);
- `HISTORY.md` and `history.d/` — what was decided and built: an item closed since November 2026 is `history.d/<id>.md` (cite it so), the older ones
  stay in `HISTORY.md` (cited as `HISTORY.md §5` or `HISTORY.md OI-6.3`), whose index of `history.d/` is written at release;
- `DEMO_RUNBOOK.md` — a live walkthrough; `docs/GUI_DEMO_GUIDE.md` — the sample rApps' demo in the operator console; `docs/call-flows/` — one sequence diagram per flow, indexed in its README (28–32: deploying, upgrading, migrating, backing up and recovering; 34–37: the converged target design);
  `<module>/docs/lifecycle.md` — each module's own lifecycle (start-up, life, stop and recovery), in the same diagram format.

The rest of this file is working practice for anyone (human or agent)
changing code here.

## Before pushing or opening a PR: run the full verification battery

Most of this is also enforced by CI (`.github/workflows/smo-tests.yml`,
which runs on every pull request, on every push to `main` and by hand;
it has no path filter, because its jobs are required checks), but run it locally
first — it's faster to iterate on a failure here than to wait on a CI
run and read its logs, and `scripts/check_migration_matches_models.py`
needs a real Postgres CI doesn't give you locally unless you start one
yourself.

**0. Lint** (CI job `lint`; the rule sets and what is switched off, and why: `ruff.toml`):

```bash
cd smo && pip install ruff && ruff check .
```

**Setup** — third-party packages come from the hashed lock in `requirements/`
(how to recompile it: `requirements/README.md`):

```bash
cd smo && pip install --require-hashes -r requirements/dev.txt && pip install --no-deps -e shared
```

**1. Every module's own unit suite** (each module's `tests/` runs
standalone against SQLite, `PYTHONPATH` pointed at both itself and
`shared/`; the suites, and what each measures, are `tests` in the modules' `module.yaml`):

```bash
cd smo
python scripts/modules.py list unit-suites | while read -r name dir source pythonpath; do
  (cd "$dir" && PYTHONPATH="$pythonpath" python -m pytest tests/ -q < /dev/null) || break
done
```

CI runs the same list under coverage (`scripts/run_unit_suite.sh`) and holds each suite to its floor, `tests.floor` in its `module.yaml`
(`scripts/coverage_floor.py`; `--write` raises the floors in the manifests).

After adding or removing tests, run `python scripts/count_tests.py --write` (or `--write --suite <module>`) and commit what changed in `docs/test-counts/`:
only the touched suites' files change (CI runs `--check`). Likewise `python scripts/config_reference.py --write` for a new or changed environment variable.

After changing anything under a sample rApp (`samples/<name>/`), rebuild its
package (`python3 samples/build_csar.py <name>`); the integration suite
fails if a committed `.csar` no longer matches its sources.

**2. Cross-service integration suite** (in-process service mesh,
`tests_integration/mesh.py` — includes the check that every committed
`docs/openapi/*.json` still matches each module's live FastAPI schema):

```bash
cd smo && PYTHONPATH=shared python -m pytest tests_integration/ -q
```

If you changed a route's request/response shape, regenerate the specs
before this check: `python scripts/generate_openapi_specs.py`.

**3. `docker-compose.yml` is structurally valid:**

```bash
cd smo && docker compose config --quiet
```

A module's compose services and its chart entries are in its `module.yaml` (`compose`, `helm`), which `python scripts/modules.py --write` writes into
`docker-compose.yml` and `deploy/helm/smo/values.yaml`. A service added to (or changed in) compose is also a module of the Helm chart: `tests_integration/test_helm_chart.py` fails when the two disagree about a
service's image, secrets, worker command or environment. With `helm` installed, `helm lint deploy/helm/smo
--kube-version 1.30.0` and that test file also render the chart.

**4. Every ORM model's columns actually exist in the migrated schema, with
matching nullability — against a real Postgres, not SQLite** (SQLite's
unit-test runs don't catch a `CHECK` constraint or a nullable/NOT NULL
mismatch the same way Postgres does — this caught a real regression
once, see `HISTORY.md` OI-6.2). Point `SMO_DATABASE_URL` at
any reachable Postgres 18 instance, or start one if you don't have one:

```bash
docker run --rm -d --name smo-verify-pg -e POSTGRES_USER=smo -e POSTGRES_PASSWORD=verify-only \
  -e POSTGRES_DB=smo -p 5432:5432 postgres:18-alpine
# the script does not create the schema: migrate every branch to its head first (Alembic, docs/adr/0001-schema-migrations.md)
cd smo && export SMO_DATABASE_URL=postgresql+psycopg://smo:verify-only@localhost:5432/smo
python scripts/migrate.py && python scripts/check_migration_matches_models.py
```

**5. GUI — typecheck, unit tests, production build, and call-flow
diagram validation:**

```bash
cd smo/gui
npm run typecheck
npx vitest run
npx vite build
npm run validate:diagrams
```

`validate:diagrams` (`gui/scripts/validate-call-flow-diagrams.mjs`)
parses every mermaid block in `docs/call-flows/*.md` with mermaid's own
parser. It exists because GitHub's mermaid renderer is stricter than it
looks from the raw markdown — a bare `;` inside a `Note over`/message
string, for instance, silently breaks the sequence-diagram grammar and
only shows up as a render error on the PR, never in a text diff. Run it
(or let CI run it) after touching any file under `docs/call-flows/`.

A call flow that has PNG images (`docs/call-flows/images/`, OPEN_ITEMS.md DOC-CF) is drawn again when its diagrams change:
`python3 scripts/render_call_flows.py docs/call-flows/<flow>.md` (needs `npm ci` in gui/ and `pip install playwright`);
`tests_integration/test_call_flow_images.py` fails on an image older than its diagram.

**6. Code documentation** (CI job `Code documentation`; the rule is `docs/CODE_DOCUMENTATION.md`):

```bash
cd smo
python scripts/check_code_docs.py          # no module worse than its file in scripts/code_docs_baseline/; every NEW file and function described
python scripts/verify_docs_only.py --base origin/main --allow-unverified-extension .md   # only for a pull request titled "Docs(code): ..."
```

Code you add must meet the rule from the day it is added. A pull request that only adds comments and docstrings is titled `Docs(code): ...`; CI proves it. If it lowers a
count, run `python scripts/check_code_docs.py --write-baseline` and commit the baseline in the same change.

**7. Contracts** (CI job `Contracts`, plan task S0.7; the bundle is `specs/smo-schema-bundle/`, its README says how a contract is written). After changing a
contract, an example, the bundle's DDL or a route a contract covers:

```bash
cd specs/smo-schema-bundle && npx --yes @redocly/cli@2.63.0 lint openapi/common/*.yaml openapi/modules/*.yaml
cd smo && pip install --require-hashes -r requirements/contracts.txt
python scripts/check_contract_bundle.py --database-url postgresql://postgres:<password>@localhost:5432/smo   # Postgres 18 with TimescaleDB (timescale/timescaledb:2.31.0-pg18)
python scripts/check_contract_drift.py      # a route a contract does not name, or a contract operation no route serves, may not grow; after it shrank: --write-baseline
```

**8. Interfaces** (CI job `Interfaces`, plan task S0.17, ADR 0011 section 7): every route in `docs/openapi/*.json` and every call of the SMO's own code
(R1Client, the three SDKs, the GUI BFF's proxy rules, the GUI) is a bundle operation, a listed ADR 0011 [D] exception, or waiting in
`scripts/interface_baseline/<module>.json` for the PR-CONV row that replaces or deletes it:

```bash
cd smo && python scripts/check_interfaces.py     # prints the per-module counts; fails on a new private route or call and on a stale baseline entry
python scripts/check_interfaces.py --write-baseline   # after a route or call was replaced or deleted: the baseline only shrinks
```

## Schema changes are revisions

The database schema is the Alembic history in `migrations/` (`docs/adr/0001-schema-migrations.md`): a shared trunk, `0001` to `0068`, and then one
**branch per module**, so pull requests of different modules never share a parent revision. To add or change a table, column, index or constraint:

1. Write a revision on your module's branch, and change the ORM model in the same PR:
   - file `migrations/versions/<label>_NNNN_<slug>.py`, `revision = "<label>_NNNN"`, where `<label>` is the module's directory name with `-` written `_`
     (`ran_nf_oam`, `aimgf`; Alembic reads `x-1` as "one before x") and NNNN counts from `0001` within the branch;
   - the branch's first revision: `down_revision = "0068"` and `branch_labels = ("<label>",)`; every later one: `down_revision` = the branch's previous
     revision, no `branch_labels`;
   - a change that needs another module's revision names it in `depends_on = "<other>_NNNN"` (`tests_integration/test_migrations.py` has the example);
   - a change no module owns (roles, extensions) goes on the `shared` branch, the same way;
   - a real `downgrade()`. Never edit `001_init.sql` or an earlier revision: a database that already ran it will not see the change. No new revision goes
     on the trunk: `scripts/check_revision_branches.py` (CI job `lint`) fails on one, on an unlabelled branch revision, a wrong parent and a second head.
2. **Until 1.0: replace, then delete (rewrite mode).** The SMO is being restructured into a converged 3GPP + O-RAN SMO
   (`docs/plan/CONVERGED_REWRITE_PLAN.md`), and the product is not live, so nothing is kept for 0.9.0 users: no deprecation window, no alias, no
   upgrade path from 0.9.0. A replaced route, table, service or SDK call is deleted in the same PR series as its replacement, and a revision may drop or
   rename in one step. Each revision still has a real `downgrade()`, and `scripts/check_migration_matches_models.py` still runs (step 3). The switch is
   `scripts/rewrite_mode.json` (plan task S0.8): while it is on, the CI jobs that compare with the previous release print a notice naming that file and
   pass without running their check: "R1 contract has no breaking change since the previous release" (`scripts/check_breaking_changes.py`),
   "Previous release's code runs on the new schema" (`scripts/check_previous_release_code.sh`), "Upgrade from the previous release keeps its data"
   (`scripts/check_upgrade_from_previous_release.sh`) and the kind lane's job `upgrade` (`.github/workflows/smo-upgrade-kind.yml`). The jobs and
   scripts stay. At 1.0, plan task S8.8 squashes the trunk and every branch into one baseline and switches these gates back on; from then the
   expand-then-contract rule of `docs/RELEASES.md` applies (a revision additive within a MINOR release, a removal or rename across two releases).
   `tests_integration/test_rewrite_mode.py` fails if the switch is still on once the release version (the newest `CHANGELOG.md` release and the
   chart's `version` / `appVersion`) is 1.0.0 or later.
3. Run `python scripts/migrate.py` (it upgrades every branch, `heads`) then `python scripts/check_migration_matches_models.py` against Postgres (step 4
   above). Nothing names a head by hand any more: `tests_integration/test_migrations.py` reads the heads from the history.
4. Add a changelog fragment (`changelog.d/<id>.md`).

Docker compose runs the migrations itself (the `migrate` service); services start only after it succeeds.

## PR conventions

- Branch names: `claude/<kebab-case-description>`.
- **Documents are part of the change.** In the same pull request, update every document the change makes stale: the overall `README.md`, the
  module's own `README.md` (HLD, LLD, unit tests), `docs/ARCHITECTURE.md` / `docs/STANDARDS.md` where behaviour or a standard's realisation changes,
  the chart's `deploy/helm/smo/README.md` for anything an operator deploys, `OPEN_ITEMS.md` or your stage's `docs/plan/rows/S<n>.md` (a closed item
  becomes a `history.d/` file), a `changelog.d/` fragment and `docs/VALIDATION.md`. A reviewer should never have to ask "where is this documented?".
- PR body: a `## Summary` (what changed and why, naming the
  `OPEN_ITEMS.md` item it closes if applicable) and a `## Test plan`
  checklist naming the specific battery steps above that were run.
- When a change closes (or partially closes) an item, delete its row (from `OPEN_ITEMS.md`, or a `PR-CONV` row from its stage's
  `docs/plan/rows/S<n>.md`) and add `history.d/<ID>.md` in the same PR, its first line `### <ID> — <title>`, with real
  implementation detail (not just "done"); `scripts/history_index.py --check` (CI) checks it. A design choice deliberately *not* taken belongs in the
  same entry, not left implicit. Keep docs current: state what the code
  does now, not how it got there.
- **The interface baseline only shrinks.** A PR that replaces or deletes a route, or moves a caller off one, also removes its entry from
  `scripts/interface_baseline/<module>.json` (`python scripts/check_interfaces.py --write-baseline`, which rewrites only the files that changed); the
  gate fails on a stale entry, and on a pull request it fails when an entry is added against the base branch. A new route is a bundle operation or a listed ADR 0011 [D] exception from the day it is added.
- **Merge when green (standing instruction from the repository owner).** After opening a PR, watch it: fix CI failures and
  review comments, and once every required check passes on the current head and the PR is mergeable: required checks green →
  `gh pr merge --squash --auto` (with the GitHub tools, enable auto-merge with the squash method); "Require branches to be up to date" stays
  off, which is what lets lane PRs merge in any order. Not required: the `github-advanced-security` check (Copilot AI findings), which fails
  when the monthly Copilot quota is spent. Don't merge on red CI, on an unresolved blocking review, or when the person running the session says
  to hold the PR. A `[cross-lane]` PR is not merged by a session: the owner merges it alone ("Working in parallel").

## Working in parallel

Several Claude Code sessions work at once, each in its own **lane** (one or a few modules), and their pull requests merge in any order with no
manual rebase. That holds as long as each pull request touches only:

- **its lane's modules** (`<module>/`: code, tests, README, `docs/lifecycle.md`);
- **its stage's rows file**, `docs/plan/rows/S<n>.md` (deleting the rows it closes);
- **its own fragments**: `changelog.d/<id>.md` and `history.d/<id>.md`, named by its task (`PR-CONV-S3.2`) or `OPEN_ITEMS.md` id, never
  `CHANGELOG.md` or `HISTORY.md`;
- **its modules' generated files**: `docs/test-counts/<module>.md`, `docs/configuration/<module>.md` and `.json`, `docs/openapi/<module>.json`,
  and its module's file in `scripts/interface_baseline/`, `scripts/contract_drift_baseline/` and `scripts/code_docs_baseline/`;
- **its module's migration branch** (`migrations/versions/<label>_NNNN_*.py`, "Schema changes are revisions");
- **its module's manifest**, `<module>/module.yaml` (schema: `scripts/module.schema.json`), and what `python scripts/modules.py --write` regenerates
  from it. A new module, or a change to a module's wiring, edits only that file: its lane, its R1 route, its compose service(s), secrets and volumes,
  its chart entry, its database role and the tables it owns, whether it has an OpenAPI spec, its unit suite and coverage floor, its mutation run, its
  code-documentation and configuration-reference files. The generated files are `docker-compose.yml`'s module regions (and the module password
  secrets of `migrate` and `pgbouncer`), the chart's `modules:` region in `deploy/helm/smo/values.yaml`, `migrations/db_roles.json` and
  `migrations/table_owners.json`, `r1-termination/app/routes.json` and the paths of `.github/workflows/smo-mutation.yml`; each module's text sits
  under a header line of its own, in path order, so two lanes' regenerated files merge without a conflict. The CI unit loop, the coverage floors,
  `scripts/generate_openapi_specs.py`, `scripts/mutation_pilot.sh` and `scripts/check_migration_matches_models.py` read the manifests when they run
  (`python scripts/modules.py list ...`). CI fails on an invalid manifest, one that disagrees with its module, and a generated file that is not current
  (`history.d/MODULE-MANIFESTS.md`).

The shared logs are assembled at release instead (`docs/RELEASES.md`, "Cutting a release": `scripts/changelog.py --write`,
`scripts/history_index.py --write`); the indexes of `docs/test-counts/` and `docs/configuration/` change only when a suite or a group is added.

A pull request that must touch genuinely shared code — `shared/`, `r1-termination/`'s code, the SDKs (`sdk/`, `sdk-go/`, `sdk-java/`), the GUI (`gui/`,
`gui-bff/`), CI (`.github/`, beyond what `scripts/modules.py --write` regenerates), the parts of `docker-compose.yml` and of the chart outside the generated
regions (the infrastructure services, the anchors, the templates, the overlays), `migrations/` outside its branch, `scripts/`, or this file — says so in
its title, starting **`[cross-lane]`**. The owner merges it alone, with no other pull request merging at the same time, and the lanes then merge `main`
into their branches. Adding a module, or changing how one is wired, is not cross-lane: it is that module's `module.yaml`. What still lists modules
outside the manifests, so that a module needing it still edits it (`[cross-lane]`): the in-process mesh of the integration suite
(`tests_integration/conftest.py`), the overlays `docker-compose.{mtls,pgtls,replicas}.yml` and `values-sized.yaml` / `values-production.yaml`, the
mTLS certificate lists (`scripts/mtls_certs.py`, `scripts/compose_mtls_check.py`), `scripts/init_secrets.sh`, `scripts/run_mypy.sh`,
`deploy/external-secrets/`, and the DAST and kind-lane module lists in `.github/workflows/` (history.d/MODULE-MANIFESTS.md says why each is left).

**Merging (the owner's GitHub setting).** The repository is owned by a personal account, where GitHub offers no merge queue. Required
checks green → `gh pr merge --squash --auto`; "Require branches to be up to date" stays off in the rule for `main`, which is what lets lane PRs
merge in any order (each lane touches only its own files, so a PR green on its own base stays green merged with the others). Allow auto-merge
in Settings → General. The `merge_group` trigger in `smo-tests.yml` is left in place; it is harmless.



## A couple of cross-cutting conventions worth knowing before you add code

- **Cross-module calls** always go through `smo_shared.r1_client.R1Client`
  (instantiated once per module as `_r1 = R1Client()`), proxied through
  R1 Termination's routing table — never a raw `httpx` call from one
  module straight to another's container.
- **Any caller-supplied notification/callback destination** (a
  `notificationDestination`/`callbackUri`/similar field accepted from a
  request body and POSTed/GETed/DELETEd back to later) goes through
  `smo_shared.webhook`'s `post_webhook`/`get_webhook`/`delete_webhook`,
  not a raw `httpx` call — see that module's docstring for why (CodeQL
  `py/full-ssrf`, and why a hostname allowlist isn't viable here). Adding
  a new callback-shaped field anywhere in this build should use it from
  the start rather than adding another ad-hoc `httpx.post` + swallow.
- **SQLite in unit tests** (`smo_shared/testing.py`'s `make_test_engine()`):
  models use Postgres types (`ARRAY`, `JSON`, `Uuid`) with a SQLite
  `.with_variant(...)` fallback. `make_test_engine()` already stores a
  Python `None` as SQL `NULL` in `JSON` columns and encodes UUIDs in the
  `ARRAY(Uuid)` fallback. SQLite returns `DateTime(timezone=True)` values
  naive, so any elapsed-time computation on such a column must normalise
  with `smo_shared.timeutil.as_utc()` first. A test suite gets the in-memory SQLite only by opting in: its `tests/conftest.py` sets
  `SMO_ALLOW_SQLITE_FALLBACK=1` before any module is imported (a new module's `tests/` needs the same file); `smo_shared.db` no longer
  guesses it from `pytest` being loaded.

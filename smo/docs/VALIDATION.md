# Validation program

What is tested today, by category, what is not, and the order in which the gaps are closed (the plan, the `V-` items, was written for 0.5.0). Every step is one PR with a CI lane, a recorded result and a line in `CHANGELOG.md`; a step that finds a defect fixes it in the same PR and says so (revision `0026` is the example: a staged CM job failed on Postgres for two releases because no test ran one there).

A lane is **gating** (every PR, under 25 minutes) or **nightly** (scheduled and by hand, results kept as a workflow artifact and summarised in the run). Load, stress and the external-facing security scans are nightly and the soak is weekly: they are slow and noisy, and a gate that is flaky teaches people to ignore it.

The number of tests in each suite and in each test file (files, test functions, collected cases) is generated from the code: [TEST_COUNTS.md](TEST_COUNTS.md). The unit and integration suites run on SQLite, which hides every Postgres-only behaviour (check constraints, schemas, roles, locks, `SKIP LOCKED`): the Postgres lanes below exist because of that.

2. V-3/V-4 (contract and breaking-change): needed by the 1.0 deprecation policy.
3. V-8 (load harness) then V-9 (stress/soak): the numbers everything after compares against.
4. V-10/V-11 (upgrade and rollback on kind), V-12 (multi-node HA).
5. V-13 (GUI browser tests), V-7 (DAST and token abuse; V-7c is decided: the external test is a criterion for 1.0.0).
6. Release candidate: every lane green, the 24 h soak run by hand, `docs/PERFORMANCE.md` and the waiver files reviewed, then Release 0.5.0 with the criteria for 1.0.0.

Every PR records: what was run, against what, the numbers, defects found and where fixed, and what remains untested. A lane that was never red is not evidence until it has been shown to fail on a seeded defect; each new test says how that was checked.

What proves them, and what only CI or a counterparty can: **unit**. `ran-nf-oam/tests/test_ves.py` (`app/ves.py` 100 %) covers the listener's switch and Basic credential (off with no password, the `*_FILE` helper, a password set twice or an unreadable file, eight kinds of bad header, none of which applies anything), the schema (both body forms, the `/eventBatch` path, a header with members missing or of the wrong type named without echoing the value, nothing applied on a bad post) and the mapping of fault, heartbeat, measurement and 3GPP performance events onto the alarm, endpoint and PM paths, with the per-event answers. `ran-nf-oam/tests/test_msac_reach.py` drives each of the ten routes of `MGT-2` for a caller with no rule, the wrong operation's rule, a DENY and the right rule, and shows that nothing changes with the switch off, for a caller that is not an Identity, and for a call that did not come through the gateway. `mock-o1-adaptor/tests/test_profile.py` covers the profile loader, the descriptor staying equal to its YANG, the stub in the profile, and the conformance kit passing it. **Integration**: `tests_integration/test_vendor_profile.py` onboards the profile at the real RAN NF OAM app, shows the registry entry equal to the stub's declaration, enforces the profile's five deviations on writes through the stub, and compares the kit's report with the one committed beside the profile; the committed OpenAPI document of RAN NF OAM now carries the VES route and its `vesBasicAuth` scheme; the contract test runs the VES route (with no password set, so every generated input must answer a documented status); the role and authentication walks cover it as a route behind the gateway. **No migration**: nothing was added to the schema, so there is no round trip to run for these changes. **Not proved.** (1) The VES mapping against a real sender: it is written from the VES 7.2 and 3GPP `perf3gppFields` schemas and exercised by the tests' own examples (`OPEN_ITEMS.md` SB-7.7). ## Code documentation (the rule, the comment-only proof and the gate)

**V-18** (done, gating, job `Code documentation`; `scripts/check_code_docs.py`, `scripts/verify_docs_only.py`, rule in `docs/CODE_DOCUMENTATION.md`). The gate counts, per module, the source files with no file description, the classes and functions that need a description and have none, and the tests with no docstring, and compares them with `scripts/code_docs_baseline.json` (first baseline, from `main`: 731 source files, 110 without a file description, 2126 of 3553 items that need a description without one, 3206 of 3683 tests without one); a module that gets worse fails, and so does any new file or function that is not described. The verifier proves that a pull request titled `Docs(code): ...` changed only comments, docstrings and layout, by comparing every changed file with the base after removing comments (Python `ast`, TypeScript syntax tree, Go tokens, Java tokens, shell/Dockerfile/YAML/Helm/SQL text). Tested in `tests_integration/test_code_docs_tools.py`: each language passes a documented version and fails a one-character change in code, a literal, a here-document, a Helm whitespace trim or a tool directive, and a throw-away repository exercises the command lines and the baseline logic. Also tried on the real tree: a header comment added to each of 754 files, and a docstring plus a `#` comment above every statement of 552 Python files, all pass; a one-character change in one file each of Python, TypeScript, Go and Java fails. The job runs in `smo-tests.yml` on every pull request; the proof step ran on the `Docs(code):` pull requests that followed (#408, #410, #417). **Limits**: the proof says the program is unchanged, not that the text is true; a docstring on a route or model changes the published OpenAPI document, which the verifier notes and the OpenAPI spec test catches; Java and shell are read with a lexer and rules, not a full parser; the TypeScript parser is the one from the GUI's toolchain (Oxc via rolldown), not esbuild or the TypeScript compiler, neither of which the GUI installs.

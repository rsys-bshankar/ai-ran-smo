# Validation program (v0.5.0)

What is tested today, by category, what is not, and the order in which the gaps are closed in 0.5.0. Every step is one PR with a CI lane, a recorded result and a line in `CHANGELOG.md`; a step that finds a defect fixes it in the same PR and says so (revision `0026` is the example: a staged CM job failed on Postgres for two releases because no test ran one there).

A lane is **gating** (every PR, under 25 minutes) or **nightly** (scheduled and by hand, results kept as a workflow artifact and summarised in the run). Load, stress, soak and the external-facing security scans are nightly: they are slow and noisy, and a gate that is flaky teaches people to ignore it.

Counts are test functions (`def test_`) at the time of writing: about 1,830 in the module and shared suites, 204 in `tests_integration`, 4 GUI files. The unit and integration suites run on SQLite, which hides every Postgres-only behaviour (check constraints, schemas, roles, locks, `SKIP LOCKED`): the Postgres lanes below exist because of that.

## 9. Rollback tests
**Today**: every Alembic revision up and down, and the schema after the round trip equals the baseline (now across every schema, with constraint definitions); the previous release's code runs on this schema (the rollback direction an operator uses); on kind, `helm upgrade` then `helm rollback` with the runbook of the old release (`.github/workflows/smo-upgrade-kind.yml`); and (V-11, second half, previous release only) a migration that cannot finish: a long transaction holds a lock on a table the newest revision alters, the migrate Job runs out of its deadline, `helm upgrade` fails, no Deployment is touched, the database keeps its revision and has nothing of the new revisions, the old release passes its runbook, and the same upgrade succeeds once the lock is gone.
**Gaps**: a migration that fails in the middle of a revision that changes data (only a blocked one is exercised: the whole migration is one transaction, so the effect is the same, but a revision's own error is not); a downgrade of the schema on a stack that is serving (the downgrade is a maintenance-window operation, not a rolling one).
**V-13** (done) the whole chain from head down to the revision above the baseline and up again over a database holding the volume (`scripts/downgrade_with_data.py`, in the volume workflow): every revision is undone in turn and timed, then applied again, and no table that exists at both ends may hold fewer rows. On 2 000 elements (20 000 alarms, 10 000 PM files) locally: 27 steps down, 0.5 to 1.1 s each, and back up in 1 s, no row lost. One real limit, now a test (`test_a_row_naming_something_that_does_not_exist_stops_the_downgrade_across_0022…`): `0022` dropped the foreign keys between modules, so a row written since that names something that does not exist makes the downgrade across `0022` fail when it puts them back; the failure is all or nothing (the database stays at the revision it was) and the same downgrade goes through once the row is dealt with. An operator who downgrades past `0022` should expect to look for such rows first (`deploy/helm/smo/README.md`).
**Plan**: **V-11** on kind: upgrade, write data, `helm rollback`, run the runbook on the old release; a migration that cannot finish leaves the old pods ready and serving (done, as a held lock rather than a test-only revision: shipping a revision that fails on purpose in every image would be code for a test); a full-chain downgrade on Postgres with data (done: V-13 above).

- a planned switchover of the three-instance Postgres to a replica (`status.targetPrimary`) with the write probe running: the gap is measured and bounded (20 s; measured 2.2 to 5.8 s, see `PERFORMANCE.md`), a row committed before is there after, the runbook gate and the audit chain pass;
- the autoscaler: metrics-server (pinned and checked), the chart installed with `autoscaling.enabled` (one replica to three, 30 % CPU), the gateway driven as fast as the answers come back; the gateway must gain a second ready replica and the calls must be answered meanwhile (at most 2 % errors); the rendered Deployment states no `replicas`, so a `helm upgrade` does not reset what the autoscaler chose.
**Gaps**: a hard node loss (power off, not a drain); a network partition between the modules and Postgres (kind's default network plugin does not enforce NetworkPolicy, so it needs another plugin in the lane); PgBouncer failover (the pooler in front of a CloudNativePG failover); zones; scale-down after the load (the autoscaler waits five minutes); the recovery time recorded per release in `docs/PERFORMANCE.md`; the whole runbook, rather than the load's mix of routes, replayed through the disturbance.

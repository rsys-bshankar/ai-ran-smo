# Energy Saving rApp demo — alignment action items (O-RAN / 3GPP)

Review list for the Energy Saving rApp demo (`smo/samples/energy-saving-rapp/`, `smo/DEMO_RUNBOOK.md` §24,
`smo/docs/GUI_DEMO_GUIDE.md`). Goal: every actor does only what the standards give it, and the demo shows the
outcome of every lifecycle step.

Target separation of roles:

| Actor | Owns in the demo |
|---|---|
| **Mock O1 (network side)** | PM generation and reporting, Digital Twin data, heartbeats, alarms, the CM state that is actually written |
| **Operator (SMO console / API)** | Onboarding and priming the package, instantiating, PM job, cell guards, **creating, training, approving and deploying the AI/ML model**, binding the model to the rApp instance, retirement |
| **Platform (SMO)** | Onboarding validation, rApp management, SME/DME, AIMgF/MLMR/MLLF, intent handling, O1 execution |
| **rApp** | Self-bootstrap over R1, data discovery, decision logic (energy saving policy), requesting inference from the deployed model, dispatching actions, verification and rollback |

Paths are relative to `ai-ran-smo/smo/`. Priority: **P1** must fix before the demo, **P2** should fix, **P3** nice to have.

## D. AI/ML model is an operator asset, not part of the rApp (P1)

### D0 — Decision
The rApp no longer registers, trains, validates, emulates, stores or deploys a model. The **operator** creates and
governs the model through the SMO AI/ML framework (MLMR, AIMgF, MLLF; TS 28.105), then **binds** the deployed model to
the Energy Saving rApp instance. The rApp only requests inference from it.

### D1 — Remove model ownership from the rApp
- **Now:** `app/main.py` `/lifecycle/train|validate|emulate|deploy` register the model in MLMR, run
  `TrainingLogic.train` **in-process**, store the artifact, drive AIMgF jobs and deploy the runtime. Inference runs
  in-process (`EnergyModel.infer`). `capabilities.yaml` declares `producedModel`, `namespace: models` and `lifecycle`.
- **Actions:**
  - [ ] Delete `/instances/{id}/lifecycle/*` routes and `/demo/emulate` from the rApp.
  - [ ] Move `app/model/` (`EnergyModel`, `TrainingLogic`, `ValidationLogic`, `EmulationLogic`, `InferenceLogic`, `series`)
        out of the rApp into a separate **model package** (e.g. `samples/energy-saving-model/`) with its own training and
        inference entry points.
  - [ ] `capabilities.yaml`: drop `producedModel`, `namespace: models`, the training/validation/emulation `lifecycle`
        stages; declare instead a **required model** (model type / input `PRB` dataset / output `recommendedState`) and
        keep only `INFERENCE` in `supportedStages`.
  - [ ] Remove the model fields the rApp owns (`model_id`, `model_version`, `artifact_version`, `model_params`,
        `lifecycle_jobs`) from `EnergySavingInstance`, or reduce them to the bound `modelId` (needs an Alembic revision:
        expand now, drop columns next release per `CLAUDE.md`).

### D2 — Give the platform a training and inference host (gap to close)
- **Now:** AIMgF training/validation/emulation jobs are bookkeeping; something external must run the work and call
  `/complete`. Today that "something" is the rApp. Inference jobs are resolved by the rApp too.
- **Actions:**
  - [ ] Add a training host (MLTF worker, e.g. `samples/energy-saving-model/trainer` or a generic `mltf-runner`) that picks up
        AIMgF training/validation/emulation jobs for its model type, reads the DME datasets
        (`PRB` history for training/testing, Digital Twin for emulation), posts progress and metrics, stores the artifact
        in MLMR and completes the job.
  - [ ] Add an inference host (MLIF runtime) that AIMgF deploys through NFO for the model, loads the MLMR artifact and
        resolves inference jobs (`POST /inference-jobs/{id}/resolve`) with the AIMLInferenceReport.
  - [ ] Document both in `docs/ARCHITECTURE.md` and call flows 02 / 17.

### D3 — Operator model workflow (new demo steps, GUI and API)
Each step shows its outcome.

## I. Instance config vs region scope: make each field mean one thing (P1)

### I0 — Problem
Demo 01 (`demo.py`) creates the instance with the same targets twice, under different key names:

```json
"config":      {"managedElementRef": "gnb-du-demo-01", "cells": ["101","102","103","104"], "actuator": "ADMINISTRATIVE_STATE"},
"regionScope": {"objectInstance":    "gnb-du-demo-01", "cells": ["101","102","103","104"]}
```

There is also a third, separate field, `authzScope` (`{"regions": [...], "tenants": [...]}`, enforced by SME). Today:
- `config` is free JSON with no schema (`rapp-mgmt/app/main.py` `CreateInstanceRequest.config`); the rApp reads its
  targets from it (`samples/energy-saving-rapp/app/main.py` `start_instance`).
- `regionScope` is free JSON too. Only Intent Service reads it (`objectInstance`, `cells` in `_scoped`), and only for
  AUTONOMOUS.
- Nothing checks that the two agree. An audience (and an operator) can't tell why the same cells are typed twice or
  which one wins.

### I1 — Target model: four fields, four questions

| Field | Question it answers | Set by | Read by | Shape |
|---|---|---|---|---|
| `authzScope` (exists) | Which part of the network may this instance **touch at all**? | Operator | SME → every module that owns a target | `{"regions": [...], "tenants": [...]}` |
| `targets` (**new**, platform field) | Which network objects does this instance **manage**? | Operator | rApp (its working set), rapp-mgmt (validation), GUI | list of 3GPP DNs (TS 32.300), e.g. `ManagedElement=gnb-du-demo-01,GNBDUFunction=1,NRCellDU=101` |
| `autonomyScope` (**rename** of `regionScope`) | Where may it **act without approval**? | Operator | Intent Service | same DN form; subset of `targets`; omitted = all targets (AUTONOMOUS) |
| `config` | How does **this rApp's own logic** behave? | Operator, within the package's schema | rApp only | only rApp tunables: `actuator`, thresholds, sleep window, … — **no targets** |

Rule: `authzScope` ⊇ `targets` ⊇ `autonomyScope`. rapp-mgmt refuses CreateInstance/Upgrade with 422 (`TARGET_OUT_OF_SCOPE`,
`AUTONOMY_SCOPE_NOT_SUBSET`) when this doesn't hold.

Energy saving instance after the change:

```json
"targets":       ["ManagedElement=gnb-du-demo-01,GNBDUFunction=1,NRCellDU=101", "...NRCellDU=102", "...NRCellDU=103", "...NRCellDU=104"],
"autonomyScope": ["ManagedElement=gnb-du-demo-01,GNBDUFunction=1,NRCellDU=101", "...NRCellDU=102"],
"config":        {"actuator": "ADMINISTRATIVE_STATE", "sleepPrbPercent": 5, "wakePrbPercent": 15, "sleepAfterMinutes": 60},
"modelId":       "<bound model, section D>"
```

### I2 — Actions
- [ ] **rapp-mgmt:** add `targets` (DN list) and `autonomyScope` to `CreateInstanceRequest`, the instance view and upgrade/rollback
      (`upgrade.py` copies `region_scope`). Keep `regionScope` accepted as a deprecated alias for one release (expand, then
      contract, per `CLAUDE.md`); Alembic revision for the new columns.
- [ ] **rapp-mgmt:** validate DN syntax, the subset rule above and `config` against the package's schema; return the reasons as
      problem details.
- [ ] **Package:** declare a config schema (e.g. `configSchema` in `manifest.yaml`, or `Files/Config/schema.json`) and the target
      object classes the rApp manages (`targetClasses: [NRCellDU]`); document in `docs/RAPP_PACKAGING.md`.
- [ ] **Energy saving rApp:** read cells from `targets` (parse the DN), not `config.managedElementRef/cells`; remove those keys
      from `config`. Same for the other three sample rApps.
- [ ] **Intent Service:** `_scoped` reads `autonomyScope` DNs (fall back to `regionScope` during the deprecation).
- [ ] **SDK:** `sdk.instance.targets()` / `autonomy_scope()` helpers so rApps don't parse JSON themselves.
- [ ] **GUI — Deploy form** (`rapps/sections/CreateInstance.tsx`; today a raw JSON textarea for `regionScope`): four labelled
      sections, not JSON boxes:
      1. *Access boundary* (authzScope) — region/tenant pickers;
      2. *Managed objects* (targets) — pick element → cells from Topology, filtered by the package's `targetClasses`;
      3. *May act alone on* (autonomyScope) — checkboxes over the chosen targets, shown only for AUTONOMOUS;
      4. *rApp settings* (config) — a form generated from the package's config schema, with defaults.
- [ ] **GUI — Instance drawer:** show the four as separate cards; mark cells in targets but outside autonomyScope as
      "needs approval".
- [ ] Docs: `DEMO_RUNBOOK.md`, `GUI_DEMO_GUIDE.md`, call flows 01/07/09, `docs/ARCHITECTURE.md`, `CHANGELOG.md`.

### I3 — Demo value
In step 11 of H2 the audience sees the operator choose *what* the rApp manages, *where* it may act alone and *how* it
behaves, as three different things. Optional negative case: put a cell in autonomyScope that isn't in targets → red 422
`AUTONOMY_SCOPE_NOT_SUBSET`. Optional ASSIST-style case without a second instance: cells 103/104 outside autonomyScope go
to **Autonomy dispatches** for approval, while 101/102 act directly.

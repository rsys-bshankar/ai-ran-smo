The flows: [34](../call-flows/34-level1-intake-and-on-demand-rapp.md) (Level-1 intake and an on-demand rApp, 11 steps),

Classes and operations are those of the schema bundle (`specs/smo-schema-bundle/`); TS 28.541 attribute names are as the published
`specs/5G_APIs/TS28541_NrNrm.yaml` (v19.6.0) spells them, and TS 28.312 targets as `TS28312_RadioNetworkExpectation.yaml` (v20.0.0) names them. What
each sample does today was read from its README, manifest, capabilities and `app/` source on `main` at 4687032.

## How to read the tables

One table per sample, one row per step of the flows. The columns:

- **Level-1 intent and targets**: what the operator asks for (a TS 28.312 `Intent` on `RAN_SUBNETWORK` `SubNetwork=BLR_12`), and the expectation
  targets. A TS 28.312 family target is [N]; a target name the family does not define is [D] (allowed as a generic target, ADR 0009 section 4.2).
- **Level-2 CM targets**: what the rApp submits to SO SMOS, as `<TS 28.541 class>.<attribute>` IS_EQUAL_TO value.
- **Model and TS 28.105 class**: the sample's model as a TS 28.105 `MLModel`, loaded by `MLModelLoadingRequest`, run in the rApp's own
  `AIMLInferenceFunction`.
- **DME data type**: R1TD v05 `ORAN:RanOamPmData:1.0.0` through the R1GAP §5.2 data services (pending in the bundle), or the [D] matrix
  `SMO:RopMatrix:1.0.0` (D-02); MDAF requests where a prediction is used.
- **Assurance goal**: what SA SMOS's `AssuranceGoal`s evaluate for the assurance intent SO SMOS hands it.
- **Possible conflicts**: what SO SMOS's write ledger and Impact Map (S5.14) would see against the other three.

A dash means the step is the same for every sample and needs nothing sample-specific. A gap (G-ES-1 and so on) is a place the sample as written today
would need special-case logic in the converged flows; each has a proposed fix and the plan task that carries it.

**Result.** None of the four maps today without special-case logic: every sample needs the common changes above, and each has its own list. All of
them fall inside plan tasks that already exist (Stage 3 contracts for the SON and coverage classes, Stage 5 for SO SMOS and SA SMOS, Stage 7 for the
samples and SDK v2), except four that need a decision: the cell-guard attributes (G-ES-3, a new ADR 0011 [D] row); the twin's scope for coverage
(G-CCO-6); and writable `CCOFunction` and `DLBOFunction` (G-CCO-1, G-TS-2), which plan task S3.14 keeps read-only today. Plan task S7.4 also leaves it to
the owner whether the coverage and traffic-steering samples move to Level-1 / Level-2 at all or are retired; this pack shows they can move. With the proposed fixes, all four go through flows 34–37 with no step of their own: the only per-sample content is the targets, the model,
the data type and the assurance goals in the tables above.

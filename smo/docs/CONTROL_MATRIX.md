# Control matrix: ISO/IEC 27001:2022 Annex A themes and NESAS/SCAS test categories

What this product does about each security control theme, with the evidence for it and an honest status (`STD-5.1`). Written from the repository (October 2026) for a reader who audits.

**What this is not.** It is not a certification, an ISMS statement of applicability or a NESAS audit. Annex A is a catalogue of controls for an organisation's management system; a software
product can address only the technical ones and contribute evidence to some organisational ones, so the people and physical themes are not applicable to it and the organisational ones are
mapped only where the repository holds an artefact. NESAS (GSMA Network Equipment Security Assurance Scheme) evaluates a vendor's development and product lifecycle processes and tests a
network product against its SCAS (3GPP security assurance specification, with TS 33.117 as the generic catalogue). **No SCAS exists for an SMO**, and no NESAS audit or SCAS test has been done on this product; the second table
maps the product to the NESAS/SCAS test categories at theme level, by name, not by requirement identifier, so that a later assessment knows where to look. The product is a reference
implementation, "not hardened or audited for production" (`SECURITY.md`): the status column says so where it matters.

**Status.** **Implemented**: the control exists and a test or CI job exercises it (named). **Partial**: some of it exists; the missing part is named, with the `OPEN_ITEMS.md` ID. **Planned**: not built; the ID that would build it. **Not applicable**: with the reason. Where the evidence lives outside this repository (GitHub repository settings), the row says **not verifiable from the repository**.

Planned for 0.5.0, as they stand in `OPEN_ITEMS.md` and `docs/VALIDATION.md` (V-7c: they come before the external penetration test): MFA and logout revocation (`SEC-7`, built; OIDC login for the GUI, `SEC-6`, is built), `/bootstrap` exposure (`SEC-9`), disaster recovery (`HA-6`). There is no separate 0.5.0 scope block in `OPEN_ITEMS.md`; the IDs are the scope.

## 3. Reading the gaps together

The gaps an auditor would find first, each with its ID: mTLS between services exists but is off by default and does not use the certificate for identity (`SEC-2`, `SEC-3.3`); Postgres TLS is built (`SEC-2.4`: `docker-compose.pgtls.yml`, the chart's `postgres.tls`) but opt in and not yet run on a cluster; MFA for operators is built but opt-in (`SEC-7`: a one-time code for local accounts, `GUI_LOGIN_MODE=oidc` to leave it to the identity provider, `GUI_ADMIN_MFA_REQUIRED` for admins), with TOTP only (no WebAuthn); disaster recovery built but not yet drilled on a real stack at size (`HA-6.3`, `docs/DISASTER_RECOVERY.md`); no threat
model (`SEC-14.1` to `14.3`); retention and erasure beyond the account (`DB-3`, `STD-4.2`, `STD-4.5`); a GUI audit log that is not tamper-evident and not backed up (`STD-4.7`, `DB-6.5`); reads of DME and MLMR not scoped per tenant
(`SEC-10.7`, the data of DME and MLMR); no external penetration test (`docs/PENTEST_SCOPE.md`, 1.0.0). Evidence that lives in GitHub settings (branch protection, required reviews, CodeQL configuration, secret scanning) cannot be
shown from the repository and is not claimed here.

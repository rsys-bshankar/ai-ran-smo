# Retention

How long each high-volume table keeps its rows, which variable changes it, and what removes the rows (`PR-DB-3`). **Nothing is deleted by default**: a retention of `0` keeps the rows for ever, so an upgrade deletes nothing until an operator sets a number. Decided October 2026: the code defaults stay at `0`, and the values in the "Proposed value" column ship in a production sample values file and in `.env.example` (`DB-3.10`, 0.6.0), not as defaults. A table whose proposed value is `keep` (the approvals and decision records, which are the evidence of who let an rApp act) has a setting like the others but no proposal: the production sample does not set it, and `.env.example` lists it as `0`. They are proposals for an operator to confirm, not legal advice; the retention a law or a contract requires is the operator's to decide (`docs/PRIVACY.md`).

## The production sample and `.env.example` (`DB-3.10`)

The "Proposed value" column is not left as prose. For **Kubernetes**, `deploy/helm/smo/values-production.yaml` sets exactly those periods (`modules.ran-nf-oam-worker.env`, `modules.ran-nf-oam.env`, `modules.mdaf-worker.env`, `modules.dme-worker.env`, `gui.env`); layer it on your values with `helm upgrade --install smo deploy/helm/smo -f deploy/helm/smo/values-production.yaml -f my-values.yaml`, and the `prod` GitOps overlay (`deploy/gitops/overlays/prod/values.yaml`) carries the same numbers. For **compose**, `.env.example` lists the variables, commented out, with the same values: copy the file to `.env` and uncomment the ones you confirm (compose passes each through to the worker). The chart's own defaults and the code's defaults stay at `0`, so installing or upgrading without those files deletes nothing. `tests_integration/test_retention_samples.py` fails when this table, the Helm sample, the GitOps overlay and `.env.example` disagree.

The GUI audit log has no worker and the chart has **no CronJob** for it, on purpose: the BFF keeps its SQLite file on a ReadWriteOnce volume that one pod may hold (it rolls with `Recreate`), so a second pod started by a CronJob could not open the file safely, or at all on another node. `values-production.yaml` puts `GUI_AUDIT_RETENTION_DAYS` and `GUI_AUDIT_EXPORT_DIR` (`/data/audit-export`, on that volume) into the gui-bff pod, and the command runs inside that pod from your scheduler: `kubectl -n smo exec deploy/gui-bff -- python -m app.retention`. Archive the export directory off the volume before it fills it. On compose: `docker compose exec gui-bff python -m app.retention`, from cron on the host.

## A table with retention off that has grown large (`DB-3.10`)

A setting of `0` is a decision to keep, but a table nobody is watching can grow until the disk fills. Each purge task therefore also looks at its table when the retention is `0`: the worker estimates the row count (Postgres: the planner's `pg_class.reltuples`, which costs no scan and is kept by autovacuum, `-1` for a never-analysed table is read as 0; SQLite: `count(*)`), sets the gauge `smo_retention_off_rows{table}` (tables `alarm`, `pm_file`, `safeguard_refusal`, `mdaf_report`, `data_record`, `rapp_action_approval`, `rapp_decision_record`; no series once retention is on), and logs **one WARNING per table per UTC day** when the estimate is above `SMO_RETENTION_WARN_ROWS` (default `1000000`; `0` never warns, the gauge stays). The gauge is served by the worker's metrics port (`SMO_WORKER_METRICS_PORT`), refreshed hourly with the task; aggregate replicas with `max`. `python -m app.retention` for the GUI audit log does the same count and warning when `GUI_AUDIT_RETENTION_DAYS` is `0`, but has no gauge: it is a command that exits, and the BFF does not install `smo_shared`, so the check is written out there. There is no alert rule yet: a table you chose to keep is not a fault, so an alert would page for a decision; graph or threshold `smo_retention_off_rows` yourself. Tested: `shared/tests/test_retention.py` (estimate, threshold, once a day, `0` never, retention on drops the series, a failed estimate never raises), `ran-nf-oam/tests/test_tasks.py`, `mdaf/tests/test_tasks.py`, `gui-bff/tests/test_retention.py`. Not tested: the `reltuples` query on a real Postgres (the unit test checks the statement, not a database).

## How it runs (`DB-3.7`)

The purges are tasks of the module's own worker (`python -m smo_shared.worker`, the single-runner of `PR-MSG-4`), so any number of workers runs a task at most once an hour across all of them, and a worker that dies frees the task for another. Each module's worker connects as that module's database role, so the purge can only touch that module's schema (`PR-DB-2`). A task is idempotent: it finds what is due from the database, deletes in batches of 1000 with a commit per batch, and may run again after a crash. A setting of `0` makes the task do nothing. The GUI audit purge is a command because the BFF is not on `smo_shared`; the same command also deletes the expired `gui_login_failure` counters, with or without `GUI_AUDIT_RETENTION_DAYS`:

```bash
GUI_AUDIT_RETENTION_DAYS=365 GUI_AUDIT_EXPORT_DIR=/var/lib/gui-bff/audit-export python -m app.retention
```

Compose passes each variable through from the environment (`.env`) to the worker; the Helm chart sets them under `modules.<worker>.env` (`ran-nf-oam-worker`, `mdaf-worker`, `dme-worker`); all default to `0`. The proposed periods are in `values-production.yaml` and `.env.example` (below).

## What is tested

`shared/tests/test_retention.py` (the purge deletes only rows older than the cutoff, leaves a row with no date, applies extra conditions, goes through more than one batch, refuses no age), `ran-nf-oam/tests/test_tasks.py` (only cleared alarms older than N days, PM files older than N days, nothing without a setting; only decided approvals, never a waiting one; only chained decision records; no `audit_log` row deleted and the chain still verifies), `mdaf/tests/test_tasks.py`, `gui-bff/tests/test_retention.py` (only the old rows, exported first, a failed export deletes nothing), `gui-bff/tests/test_account_cooldown.py` (the counter purge removes expired rows of all three kinds and the old name-only ones and keeps live ones, and `python -m app.retention` runs it with the audit retention off and on), `tests_integration/test_retention_samples.py` (the samples agree with this table and the defaults keep everything). Not tested: a purge against Postgres at volume (the unit tests run on SQLite), and the time a purge takes on a table of millions of rows.

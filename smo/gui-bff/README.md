# SMO Operator GUI BFF (`gui-bff/`)

> The only API the operator console's browser talks to: it owns GUI users, sessions, role-based access and the audit log, and forwards allowed calls to R1 Termination with its own SME-issued OAuth2 token.

## 1. High-level design (HLD)

### 1.1 Purpose and scope

The BFF exists so that the browser never calls R1 Termination or a module port directly (that would need CORS on every module and bypass role checks). It:

- authenticates GUI users (password login, httpOnly session cookie, or an OAuth2 password-grant Bearer token for scripts), with a one-time code after the password for an account that has one (section 2.10), and, when switched on, through an OpenID Connect provider (section 2.9);
- holds the user and role table and checks every proxied call against it (`app/rbac.py`);
- pins identity-bearing request fields to the signed-in GUI user instead of trusting the browser;
- authenticates to the SMO as an ordinary R1 consumer (CAPIF invoker at SME, `client_credentials`);
- writes an append-only audit log;
- aggregates module health.

It implements no SMO domain logic: lifecycle rules stay in the modules, and the BFF is a policy-enforcing pass-through.

### 1.2 Standards basis

None. Reused conventions only: RFC 6238 (TOTP) and RFC 4226 (HOTP) for the one-time codes, the Key URI Format of the authenticator apps for the `otpauth://` link, RFC 6749 section 4.3 (resource-owner password grant, `POST /api/token`), OpenID Connect Core 1.0 and Discovery 1.0 with RFC 7636 PKCE and RP-Initiated Logout 1.0 for the optional OIDC login (section 2.9), RFC 7519 (HS256 session JWT, hand-rolled verifier in `app/security.py`), and the CAPIF invoker onboarding plus client-credentials path the SMO already exposes ([`../../specs/5G_APIs/`](../../specs/5G_APIs/) `TS29222_CAPIF_API_Invoker_Management_API.yaml`) for its southbound identity. Its error bodies are `{title, status, detail}` shaped like the R1 ProblemDetails convention but deliberately do not use `smo_shared` (see 1.5).

### 1.3 Position in the platform

```
Browser --/api--> gui (nginx :3000) --> gui-bff --Bearer (SME-issued)--> R1 Termination --> modules
                                           |                                   ^
                                           +-- own SQLite: users, audit, SME credential, sign-ins in flight
                                           +-- (optional) OIDC provider: discovery, JWKS, token endpoint
                                           +-- /bootstrap, SME onboarding + token ---+
```

- Calls: only R1 Termination (and SME's token/registration endpoints at the address R1 advertises), and, with OIDC on, the one configured identity provider (`GUI_OIDC_ISSUER`). Never a module container directly.
- Never touches: the SMO Postgres database, `smo_shared`, any module port.
- Publishes no host port (`docker-compose.yml`).
- It does not set `X-Correlation-ID`; R1 Termination mints one per proxied request (call flow 14).

### 1.4 Ownership

| Owns | Does not own (owner) |
|---|---|
| GUI users, roles, password hashes, session revocation counter | rApp / SMO identities (SME, rApp Management) |
| The RBAC table mapping `METHOD + /<module>/...` to a minimum role | The semantic validity of any proxied request (the target module) |
| Append-only GUI audit log | Platform-side audit or fault data (RAN NF OAM, FOCOM) |
| The BFF's own CAPIF invoker credential at SME | SME's invoker registry and token issuance (SME) |
| Health, readiness and build-version aggregation across modules (`GET /api/modules/status`) | Module health endpoints themselves (each module) |
| The console's summary counts, their event stream and the typeahead: computed from module reads, cached in the process (`/api/summary`, `/api/events`, `/api/search`) | The counted and searched data (each module); raw domain events (none is published to the BFF) |

### 1.5 Design decisions

| Decision | Reason |
|---|---|
| Allowlist RBAC, first match wins, unmatched = refused for everyone | A new module route is unreachable from the GUI until someone adds a rule. Machine-to-machine routes (SME token/registration, DME producer registration, NFO Instantiate, heartbeats, `usage/*`) are simply absent. |
| Role read from the `gui_user` row on every request, never from the JWT | A demotion applies on the next request. |
| JWT carries `ver` = `gui_user.token_version`; bumped on password change/reset and on (de)activation | Existing sessions die at once without a session store. Self password change re-issues the caller's own token. |
| Cookie session plus double-submit CSRF: `smo_csrf` cookie (readable) echoed as `X-CSRF-Token`, compared with the `csrf` claim inside the JWT | Applies only to cookie-authenticated `POST/PUT/PATCH/DELETE`. A Bearer call needs no CSRF (a browser never attaches one by itself). |
| Cookies: `smo_session` HttpOnly, `Path=/api`; `SameSite=Strict`; `Secure` by default (`GUI_COOKIE_SECURE`) | Session unreachable from script and not sent to non-API paths. |
| OIDC (PR-SEC-6): authorization code with PKCE, opt in, one provider; the session after it is the same signed cookie, CSRF token and `jti` as a password login; the identity provider does the second factor for its users | Section 2.9 has the flow and what was not taken. |
| Two layers of multi-factor (PR-SEC-7): (1) `GUI_LOGIN_MODE=oidc` makes the identity provider the only way in, so its MFA applies; (2) a one-time code (TOTP) after the password for local accounts, mandatory for admins when `GUI_ADMIN_MFA_REQUIRED` is on, and the login of the break-glass account | Section 2.10. A local account is what remains when the provider is down, so it needs its own second factor. |
| HS256 (the default) verified with stdlib `hmac`, fixed header, constant-time compare, `exp` required | No `alg` negotiation to get wrong; no JWT library for the default session token. |
| Optional RS256 / ES256 session token with a `kid` and a published key set (PR-SEC-5, `GUI_JWT_ALGORITHM`) | Off by default. The header `alg` must be exactly the configured one, the key is chosen by `kid` from the configured set and never from the token, so `none`, algorithm confusion and a token that brings its own key fail before any signature is checked. PyJWT (`pyjwt[crypto]`, already locked for the OIDC ID tokens) does the asymmetric maths; section 2.11 has the details and what was not taken. |
| scrypt (N=2^14, r=8, p=1, 16-byte salt) password hashes; unknown user verifies against a dummy hash | Response time does not reveal which usernames exist. |
| Local `_problem()` / `_paginate()` instead of `smo_shared` | The BFF's CI job and image deliberately do not depend on `smo_shared`; the BFF must also keep working (login, audit) while the SMO stack is down. |
| Own small store, not the SMO Postgres schema | None of it is SMO domain data. |
| Identity pinning in RBAC rules (`query_overrides`, `json_overrides`) | `ack_user_id`/`clear_user_id`, SA SMOS `requester_is_admin`, CM-write `requestedBy` + `msacRole`, DME `/dme/actions` `requestedBy`, Intent `rmioId`/`requesterId` (`smo-gui`), ASSIST reject `rejectedBy`, energy-saving override `operator`, global rApp stop `requestedBy`, SSH host-key `pinnedBy` are overwritten from the session. |
| `query_match` checks every value of a repeated parameter | `?event=CERTIFY&event=DEPRECATE` cannot slip past the admin rule whichever value the backend reads. |
| Proxy forwards only `Content-Type` and `Accept`; strips hop-by-hop, `content-length`, `content-encoding`, `set-cookie`, `server`, `date` from the response | Browser credentials never reach R1; an upstream `Set-Cookie` never reaches the browser. |
| BFF JSON responses carry `CSP default-src 'none'; frame-ancestors 'none'`, `nosniff`, `X-Frame-Options: DENY`, `Referrer-Policy: no-referrer`, `Cache-Control: no-store` | Nothing the BFF serves may be framed, sniffed or run. |
| Secrets from the environment only; a generated admin password goes to a mode 0600 file, never the log | See `config.py`, `seed_users`. |
| Failure behaviour | SME/token failure: 502 `SMO_AUTH_FAILED`. R1 unreachable: 502 `R1_UNREACHABLE`. Upstream errors pass through verbatim. Exception text is never put in the response `detail`. |

Idempotency: none needed beyond `seed_users` (first boot only, never touches a non-empty user table) and user DELETE (204 whether or not the user existed).

### 2.2 Data model

`gui_user_preference` (the GUI redesign): `username` (primary key), `value` (the preferences as JSON text, validated by `app/preferences.py` before it is stored), `updated_at`. A new table made by `create_all`; a deleted user's row is deleted with the account.

**`gui_export_job`** (GUI-9.5b, `app/exports.py`): one asynchronous CSV export. New table made by `create_all`; in the database so that every instance on a shared `GUI_DATABASE_URL` lists the job and serves its file.

| Column | Notes |
|---|---|
| `id` | UUID, PK |
| `username` | who asked (index on (`username`, `created_at`)) |
| `kind` | `decisions` (role operator) or `audit` (role admin) |
| `params` | JSON: `since`, `until` (filled with the request time when not given) and the filters given (`invokerId`, `disposition`, `region`, `siteCluster`; `username`, `action`) |
| `state` | `QUEUED` → `RUNNING` → `DONE` or `FAILED`; `EXPIRED` is shown (not stored) for a finished job past `expires_at` |
| `rows`, `bytes` | written so far (updated after every source page), final when DONE |
| `error` | why it FAILED (`interrupted: ...` for an orphan); for a DONE job that reached 10,000,000 rows, the note that the file stops there |
| `created_at`, `finished_at` | UTC |
| `expires_at` | indexed; creation + 24 h, then finish + 24 h. Expired jobs (and their chunks) are deleted by the next `POST /api/exports` of any user |
| `runner_id` | the process (a random id per BFF process) whose asyncio task runs the job (so a read can tell a job whose task died in this very process) |
| `heartbeat_at` | written by the task at every page; a QUEUED or RUNNING job whose heartbeat is older than 90 s (or whose `runner_id` is this process and has no task here) lost its instance and is marked `FAILED` "interrupted" when read |

**`gui_export_chunk`** (GUI-9.5b): `job_id` (FK to `gui_export_job.id`, `ON DELETE CASCADE` where the database enforces it; the BFF also deletes them itself) and `seq` (from 0) together the PK, `data` (bytes, at most 1 MiB; the file is the chunks concatenated in `seq` order, a chunk may end inside a row). Chunks whose job is gone (deleted while another instance was writing) are removed by the same purge.

Own database (`GUI_DATABASE_URL`, default `sqlite:///./gui-bff.db`; compose uses `sqlite:////data/gui-bff.db` on the `gui_bff_data` volume). Tables are created by `Base.metadata.create_all`; none of them is in `migrations/001_init.sql` or the Alembic history (`migrations/`, which is the SMO's Postgres schema), so a PR-SEC-7 "revision" does not exist: a table that is new is made by `create_all`, and a column added to a table that exists (`gui_user.break_glass`) is added by `Database._add_missing_columns` with `ALTER TABLE ... ADD COLUMN ... NOT NULL DEFAULT false` (expand only: the previous release's code, which neither reads nor writes it, keeps working on the upgraded file, and a second instance racing to add it finds it there).

**`gui_user`**

| Column | Notes |
|---|---|
| `username` | PK; creation validated against `^[a-z][a-z0-9_.-]{1,31}$`; an OIDC user is `oidc:<subject>` (the colon keeps it apart from every local name) |
| `password_hash` | `salt_hex:digest_hex` (scrypt); `!` for a user of the identity provider, which can never verify (no password stored) |
| `role` | `viewer` / `operator` / `admin` |
| `active` | default true |
| `token_version` | seeded users start at 0, a user created through the admin route at a random value (so a user deleted and created again under the same name does not accept the earlier holder's token); bumped on password change/reset and on any `active` change |
| `break_glass` | PR-SEC-7.7, default false: an admin flagged this local account as the break-glass login (`PATCH /api/admin/users/{name}` `breakGlass`) |
| `created_at` | UTC |

**`gui_audit_log`** (append-only: a `before_flush` listener raises `PermissionError` for any dirty or deleted `AuditEntry`)

| Column | Notes |
|---|---|
| `id` | autoincrement PK |
| `at`, `username`, `role` | `username`/`role` nullable (e.g. failed login for an unknown name has no role) |
| `action` | `LOGIN`, `LOGIN_FAILED`, `LOGIN_LOCKED`, `LOGIN_REFUSED`, `MFA_CHALLENGE`, `BREAK_GLASS_LOGIN`, `RECOVERY_CODE_USED`, `OIDC_LOGIN`, `OIDC_LOGIN_FAILED`, `TOKEN`, `LOGOUT`, `PASSWORD_CHANGED`, `TOTP_ENROL_STARTED`, `TOTP_ENROLLED`, `RECOVERY_CODES_REGENERATED`, `TOTP_RESET`, `USER_CREATED`, `USER_UPDATED`, `USER_DELETED`, `USER_SESSIONS_REVOKED`, `PROXY`, `DENIED` |
| `method`, `path`, `status_code`, `detail` | proxy calls; `path` includes the query string for mutating calls |

Index `ix_gui_audit_log_username_id` on (`username`, `id`) (GUI-9.8): a user's own sign-ins and the last-active time per user. A database made before it gets it from `Database._add_missing_indexes` (`CREATE INDEX IF NOT EXISTS`, expand only). The `action` values also include `AUDIT_EXPORTED` (an admin downloaded `/api/admin/audit.csv`; `detail` holds the filters), `RAPP_ACTION` (PR-GUI-8) and `USER_*` as listed.

**`gui_oidc_login`** (PR-SEC-6): one OIDC sign-in in flight, written by `GET /api/oidc/login` and deleted by the callback: `state` (PK), `nonce`, `verifier` (the PKCE code verifier), `binding_hash` (SHA-256 of the value in the browser's `smo_oidc` cookie), `expires_at` (indexed; ten minutes). In the database, not in a process, because the callback may land on another instance. Contains no personal data. Expired rows are removed whenever a sign-in starts; at most 5000 may wait (the route is unauthenticated).

**`gui_user_totp`** (PR-SEC-7.1): one row per local user with a one-time code: `username` (PK), `secret_enc` (`v1:` + base64 of nonce and AES-256-GCM ciphertext of the base32 secret, the user name as associated data; never the secret), `confirmed` (false until the first valid code from it: an unconfirmed row is an enrolment in progress and is never used to sign in), `last_step` (the time step of the last code accepted; the replay guard, shared by every instance), `created_at`, `confirmed_at`.

**`gui_recovery_code`** (PR-SEC-7.3): ten rows per enrolled user: `id`, `username` (indexed), `code_hash` (HMAC-SHA256 under a key derived from `GUI_TOTP_KEY`, over the user name and the code), `used_at` (set the one time the code is spent).

**`gui_login_challenge`** (PR-SEC-7.2): the second step of a sign-in in flight: `jti` (PK), `username`, `expires_at` (indexed; five minutes). Written when the password was right, deleted when the code was right (a `DELETE` whose row count decides, so it works once, on any instance); expired rows are removed whenever one is written.

**`gui_smo_credential`** (one row, `id=1`): `api_invoker_id`, `onboarding_secret`. Stored as issued because it must be presented to SME's token endpoint, so it cannot be hashed here.

**`gui_rapp_pin`** (PR-GUI-8.5): the rApp instances a user pinned to the sidebar, at most `MAX_PINS` (5) each: `username` and `instance_id` (together the PK; the instance is a bare reference into rApp Management, with no foreign key), `pinned_at`. A new table made by `create_all`, so `_add_missing_columns` has nothing to add for it. Deleting a user deletes the rows; a pin of an instance that no longer exists is dropped when the pins are read.

### 2.3 State machines

None: stateless. The only state is per-user `token_version` and `active` (no transitions beyond what 2.4 lists), plus the SME token cache (2.5). The signing key, the login-failure counters and the SME credential are database rows, shared by every instance of the database.

### 2.4 API

Every list route also takes the optional `total` (boolean, default `true`, the shared `smo_shared.pagination` parameter): `total=false` skips the `COUNT(*)` of the whole result, leaves `total` out of the envelope and adds `hasMore`.

All routes are under `/api`, except `GET /.well-known/jwks.json` (below). OpenAPI is served at `/api/openapi.json` (docs/redoc disabled); there is no committed `../docs/openapi/gui-bff.json`, and the BFF is not one of the modules the contract tests (`tests_integration/test_contract_schemathesis.py`) and the route-table walk (`tests_integration/test_authz_walk.py`, which walks the backends behind R1 Termination) cover: the BFF's own routes are covered by this module's tests (`tests/test_signing.py` for the key set route).

**Signing keys** (PR-SEC-5)

| Method | Path | Purpose | Notable errors |
|---|---|---|---|
| GET | `/.well-known/jwks.json` | The public keys that verify session tokens, RFC 7517: `{"keys": [{kty, use: "sig", alg, kid, and n, e or crv, x, y}, ...]}`, the current key first, then the previous rotations. Under HS256 (default) `{"keys": []}`: a shared secret has no public half and is never published. No session, no CSRF: public by design (it is the public half). `200 application/json`, `Cache-Control: public, max-age=300`, the BFF's usual security headers. The GUI's nginx forwards this one exact path to the BFF | none: it answers 200 whatever the algorithm (an invalid key stops the start, not the route) |

**Auth and session**

| Method | Path | Purpose | Notable errors |

`decide(declaration, instance, method, path, role, ...)` refuses in this order, and each refusal is a `DENIED` audit row: a declaration that is not the validated shape (it never raises): 403 `UNDECLARED_ROUTE`; a change on a `readOnly` rApp: 403 `RAPP_READ_ONLY`, for every role, before the route is looked at; a route that is not declared **for this instance** (`{instanceId}` is the page that is open: another rApp's id in a declared route is refused, as is `..`, `%`, `//`, a backslash or a segment outside `A-Za-z0-9._~-`): 403 `UNDECLARED_ROUTE` whatever the role; the role (a read needs viewer, a change operator): 403 `FORBIDDEN`. Then **a read** sends only the query its source declares: a fixed value is the declared one whatever the browser sent, a whole-value `{row.<field>}` is the browser's value and must be one safe segment (422 `INVALID_QUERY`), anything else is dropped. **A change** sends a JSON object of the declared inputs (checked for type, bounds, length and enum options, a missing required one is 422 `INVALID_INPUT`, a field that is not an input is dropped) and the fixed `body`, in which the string `"{user}"` is replaced by the session's user and a fixed value cannot be overridden; a DELETE sends no body; more than 64 KiB is 413. `when` of a row action is not enforced here: it is a presentation rule on the row the browser holds. **Audit:** a change writes a `RAPP_ACTION` row `phase=requested` (before the call is sent, so a change that never reached the rApp is still known) and another `phase=done` with the status (502 with the cause's title when the SMO could not be reached), each naming the instance and the action id. The BFF keeps the package index (name, version, vendor, `hasPage`) for 30 s (read again at once when a listed instance's package is not in it, at most every 2 s: a rApp onboarded at run time shows with its name) and a declaration for 60 s, in this process only.

Rule evaluation (`decide`): rules are scanned in order; a rule matches on method, a fully anchored path regex (`{id}` = `[^/]+`, so ids cannot span segments) and every `query_match` pair. The first match decides: allowed iff the caller's rank is at least the rule's role. No match: refused with no required role. The single `viewer` rule is the final catch-all `GET /(<modules>)(/.*)?`; the one sensitive read before it (`GET /aimgf/feature-groups` and `/aimgf/feature-groups/{name}`, which carry datalake tokens) requires operator. Of the 150 rules, 72 require operator, 77 admin, 1 viewer. For the per-role summary see [`../gui/README.md`](../gui/README.md#roles); the rule list in `rbac.py` is the source of truth.

### 2.5 Interactions

**Southbound token (`R1Gateway`)**: (1) `GET {R1}/bootstrap` for the `tokenEndPoint` URI (skipped when `SME_URL` is set: `{SME_URL}/oauth2/token`); (2) if `gui_smo_credential` is empty, `POST {sme}/invoker-registrations` with an opaque `apiInvokerPublicKey` and persist the returned `apiInvokerId` + `onboardingSecret`; (3) `POST` the token endpoint with `grant_type=client_credentials`, scope `smo-gui`. If SME answers 400 (invoker unknown, e.g. its DB was reset) the BFF onboards afresh once. The token is cached until `expires_in` minus 30 s (minimum 1 s) under an `asyncio.Lock`. Any `httpx.HTTPError` or non-200 becomes `SmoAuthError`.

**Proxy call**: `R1Gateway.request()` attaches `Authorization: Bearer`; if R1 answers 401 it fetches a fresh token and retries exactly once. Timeout `GUI_UPSTREAM_TIMEOUT_SECONDS`.

**Health probe**: `GUI_HEALTH_TIMEOUT_SECONDS` per module; a `SmoAuthError` reports `error: "auth: no SMO access token"`, a transport error `error: "unreachable"`, and one failing module never fails the endpoint.

**Audit rules**: every sign-in event, user admin action, every `DENIED` proxy call (any method), and every mutating proxied call (`POST/PUT/PATCH/DELETE`, with the final upstream status and the query string; a 502 is recorded with the cause) is written. Allowed reads are not audited.

**Background tasks**: none. In-process state: the login-failure map (`username -> (count, first_failure_time)`) and the cached SME token.

**Login lockout**: 5 failures (`MAX_LOGIN_FAILURES`) inside 300 s (`LOCKOUT_SECONDS`) lock the account for the rest of that window (429 `TOO_MANY_ATTEMPTS`, audited `LOGIN_LOCKED`); a completed sign-in clears the counter. A wrong password, a wrong one-time code at the second step, a wrong recovery code, a wrong code typed to confirm an enrolment or to make new recovery codes, and a wrong `otp` at the token grant all count in the same counter, and the password step does not clear it (only a finished sign-in does), so a guesser who knows the password gets five code guesses in all, not five per password round. This is the rate limit of the second step; a limiter per client address on the login routes is `SEC-8.6`, still open. The counters are rows in `gui_login_failure`, keyed by the username as typed (an unknown name is counted and locked exactly like a real one, so the lockout does not reveal which usernames exist), updated atomically in SQL, so every instance sharing the database counts the same failures.

### 2.8 Limits and open items

- Sessions are signed tokens with no session list: `POST /api/logout` clears the cookies and records the token's `jti` in `gui_revoked_session` until the token would expire, so a copied cookie or Bearer token stops working on every instance. An admin ends every session of one user with `POST /api/admin/users/{username}/revoke-sessions` (it bumps the user's `token_version`); there is still no list of a user's sessions to pick one from.
- Running more than one instance needs one shared database: set `GUI_DATABASE_URL` to the same Postgres (or similar) for all of them. The default SQLite file belongs to one instance, and two instances on separate files would have separate users. When seeding on first boot, set `GUI_ADMIN_PASSWORD` explicitly: with a generated password each instance writes its own password file, and an instance that loses the seeding race deletes the one it wrote.
- The SME token cache is per process (a token is per process by nature); an expired or revoked token is refreshed once on a 401.
- One OIDC provider at most, no LDAP bind (`SEC-6.8`, optional, open). Users and roles still live in `gui_user`; R1 Termination's own OAuth is unchanged.
- No per-module data validation on `/api/smo/...`: an operator can submit anything the module accepts; the BFF checks role only. The calls to a rApp's operator API are the exception: they are checked against the rApp's declaration (2.4).
- The BFF cannot know the rows of a rApp's table, so it cannot check that a `{row.<field>}` value in a declared call is the value of a real row; it enforces that the value fills only the places the declaration names, is one safe segment, and the rApp's own checks apply to the rest. A rApp's page shows nothing for an instance whose `operatorApiBase` is not registered.
- `/api/modules/status` probes R1 and the 15 SMO modules; the sample rApps are no longer modules of it (they are rApps, listed in the directory).
- The RBAC regexes are mirrored in the SPA (`../gui/src/auth/permissions.fixture.json`); regenerate with `cd gui-bff && PYTHONPATH=. python scripts/export_permissions.py` after editing `rbac.py` (`test_rbac.py` fails on drift).
- One-time codes: TOTP only (no WebAuthn / security keys, no SMS or e-mail codes, no push), no QR image (the secret and the `otpauth://` link are shown for typing: no rendering dependency), no self-service removal of a code (an admin resets it), no trusted-device ("remember this browser") bypass. A lost key (`GUI_TOTP_KEY`) makes every stored secret unreadable; rotating it is a reset of every user's code (`SECRETS.md`).
- Export jobs (GUI-9.5b) run in the instance that accepted them: an instance that stops (or crashes) leaves its jobs `FAILED` "interrupted" (at once on a clean stop, otherwise when read after 90 s without a heartbeat); they are not resumed elsewhere. The file lives in the BFF database until 24 h after the job ended, so a 10,000,000-row export takes that much room in `GUI_DATABASE_URL` meanwhile. The per-user limit of 3 is checked then inserted, so two requests at the same instant can make a fourth.
- No OPEN_ITEMS id refers to this module.

### 2.9 OIDC login (PR-SEC-6)

Off by default (`GUI_OIDC_ENABLED=false`): nothing below exists then, `/api/oidc/*` answer 404 and `GET /api/auth/config` says `oidc.enabled: false`. Local username/password login is unchanged and stays as the break-glass admin path. Every variable is in `../docs/CONFIGURATION.md`; the ones that matter: `GUI_OIDC_ISSUER`, `GUI_OIDC_CLIENT_ID`, `GUI_OIDC_CLIENT_SECRET[_FILE]`, `GUI_OIDC_REDIRECT_URI` (the public URL of `/api/oidc/callback`, registered at the provider), `GUI_OIDC_SCOPES`, `GUI_OIDC_GROUPS_CLAIM`, `GUI_OIDC_GROUP_ROLE_MAP`, `GUI_OIDC_DEFAULT_ROLE`, `GUI_OIDC_PROVIDER_NAME`, `GUI_OIDC_POST_LOGOUT_REDIRECT_URI`, `GUI_LOCAL_LOGIN_ENABLED`. `OidcConfig.from_settings` checks the combination when the app is built, so a missing issuer, a non-https URL (http only for localhost or with `GUI_OIDC_ALLOW_HTTP`), `openid` missing from the scopes, a bad role in the map, or "nobody could sign in" (no map and no default role) stops the start and names the variable.

**The flow.**

1. The sign-in page (`gui/src/pages/Login.tsx`) asks `GET /api/auth/config` and, when OIDC is on, shows a link "Sign in with <provider name>" to `/api/oidc/login` (a full navigation, not a fetch).
2. `GET /api/oidc/login` creates `state`, `nonce`, a PKCE verifier (S256 challenge) and a browser-binding value; stores `state`, `nonce`, the verifier and the SHA-256 of the binding value in `gui_oidc_login`; sets the binding value as the cookie `smo_oidc` (HttpOnly, `SameSite=Lax` because the provider's redirect back is a cross-site navigation that `Strict` would not carry, `Path=/api/oidc`, ten minutes); and answers 302 to the provider's authorization endpoint, found by discovery.
3. The provider authenticates the person (and enforces multi-factor: the BFF asks a user of the identity provider for nothing more, section 2.10 is for local accounts) and redirects to `GET /api/oidc/callback?code=...&state=...`.
4. The callback consumes the `gui_oidc_login` row by `state` (a `DELETE` whose row count decides, so a replay, an expired state or a second instance racing for it finds nothing), checks the `smo_oidc` cookie against `binding_hash` (so a callback URL planted in another browser, login CSRF, does not work), exchanges the code at the token endpoint with the verifier (client authentication `client_secret_basic`, or `client_secret_post` when that is all the provider offers, or none for a public client), and validates the ID token.
5. **ID-token validation** (`OidcClient.validate_id_token`): the algorithm must be one of RS256/384/512, PS256/384/512, ES256/384/512 (so `none` and an HMAC keyed with the public key are refused before any key is looked at); the signature is checked against the JWKS key with the token's `kid`; `iss` equals the configured issuer; `aud` contains the client id, and `azp` equals it when present or when there are several audiences; `exp`, `iat`, `sub`, `iss`, `aud` are required, with 30 s of clock leeway; `nonce` equals the one this sign-in started with; `at_hash`, when the token has one, matches the access token.
6. **Role.** The claim named by `GUI_OIDC_GROUPS_CLAIM` (a list, or a string split on spaces and commas; a dotted name reaches into an object, such as `realm_access.roles`) is looked up in `GUI_OIDC_GROUP_ROLE_MAP` (`group=role,...`); the highest role matched wins; none matched gives `GUI_OIDC_DEFAULT_ROLE`, which is empty by default, and empty means refused (`no_role`). The ID token alone is used: the userinfo endpoint is not called.
7. **User.** Provisioned just in time as `gui_user` `oidc:<subject>` with `password_hash = "!"` (no password is stored and none can verify, so the row cannot be used at `/api/login`). The role is set from the token at every sign-in, and a changed role is noted in the audit row; a role an admin sets by hand on the Users page is therefore overwritten at the next sign-in. A user with `active = false` is refused (`account_disabled`). A user who signs in with no mapped group has the `token_version` of an existing row bumped, which ends that person's earlier sessions. An admin cannot set a password on such a user (409 `OIDC_USER`); deleting the user works as for any other, and the next sign-in creates it again.
8. **Session.** The same as a password login: `issue_session` (HS256 JWT with `ver`, `csrf`, `jti`), `smo_session` and `smo_csrf` cookies set on the 303 to `/`, the `smo_oidc` cookie cleared. Everything after that (CSRF double submit, revocation by `jti`, `token_version`, role read from the row on every request) is the existing machinery.
9. **Audit.** `OIDC_LOGIN` (username `oidc:<subject>`, role, detail `iss=<issuer>` and whether the user was created or the role changed) and `OIDC_LOGIN_FAILED` (the subject when the token was valid enough to have one; detail is a reason code, a validation class name or a claim name, never a token, a code or the provider's text). The browser is only given the reason code, as `/login?oidc_error=<code>`, and the page maps it to its own wording.

**Provider documents.** Discovery (`<issuer>/.well-known/openid-configuration`; its `issuer` must equal the configured one, and the endpoints it names must be https) and the JWKS are fetched with `GUI_OIDC_TIMEOUT_SECONDS` and cached in the process for an hour; a cache of public provider metadata is safe per replica. A `kid` the cache does not know makes one refetch (key rotation), at most once per 30 s so a forged `kid` cannot make the BFF hammer the provider; a provider that cannot be reached leaves the last good copy in use. Only RSA and EC signing keys (`use` absent or `sig`) are kept.

**Logout.** `POST /api/logout` revokes the session as before. For an `oidc:` user, when the provider's discovery document has an `end_session_endpoint`, the answer also carries `endSessionUrl` (`?client_id=...` and, if `GUI_OIDC_POST_LOGOUT_REDIRECT_URI` is set, `post_logout_redirect_uri`), and the SPA sends the browser there (RP-initiated logout) so the provider's session ends too. No `id_token_hint` is sent: the BFF keeps no ID token, so the provider may ask the person to confirm.

**Break-glass.** `GUI_LOCAL_LOGIN_ENABLED` (default `true`) keeps `/api/login` and the `/api/token` password grant; `false` answers both 403 and hides the form, and is refused at start unless OIDC is on (otherwise nobody could sign in). It overrides everything in section 2.10: with it off there is no break-glass account either. `GUI_LOGIN_MODE=oidc` is the milder switch: the form stays for break-glass accounts only.

**Not taken.** Native MFA for provider users (the provider does it; the local layer is section 2.10); storing the ID token (for `id_token_hint`, and to avoid a PII copy); calling the userinfo endpoint; several providers; mapping the e-mail or `preferred_username` to a readable name (a `gui_user` row is keyed by name and the schema is not changed in a minor release, so the subject is the name and the audit row names the issuer); an OIDC back-channel logout; LDAP (`SEC-6.8`).

### 2.10 Multi-factor sign-in (PR-SEC-7)

Two layers, decided together. Layer 1 is a setting, layer 2 is code in this module. Nothing changes by default: `GUI_LOGIN_MODE=both`, no key, no admin requirement, and an account without a one-time code signs in with its password exactly as before.

**Layer 1: the identity provider's MFA (`GUI_LOGIN_MODE`).** With `oidc` the BFF refuses the password for every account except a break-glass one, so the only way in is the provider, whose policy (Keycloak required actions, Entra Conditional Access, Okta policies) applies. `POST /api/login` first checks the password as always (a wrong one is still 401 `INVALID_CREDENTIALS`, counted; an unknown name still takes the dummy-hash time), and only then answers a correct password of an account that is not break-glass with 403 `LOGIN_MODE_OIDC_ONLY` and an audit row `LOGIN_REFUSED`: the refusal tells nothing about which names exist, and does not open anything. `POST /api/token` answers 403 `unauthorized_client` in the same case. `GET /api/auth/config` reports `localLogin: false`, so the page shows only "Sign in with <provider>". The start is refused when the mode is `oidc` and OIDC is not configured. Mode `local` builds no OIDC client at all (a leftover provider setting cannot stop the start) and `/api/oidc/*` answer 404.

**Layer 2: a one-time code for local accounts.**

- *Algorithm* (`app/totp.py`): RFC 6238 on the standard library: HMAC-SHA1 (what every authenticator app does), 30 s step, 6 digits, base32 secret of 160 random bits. A code is accepted for the previous, the current and the next step (clock drift); all three are compared in constant time. The unit tests run the RFC 6238 and RFC 4226 test vectors.
- *Replay.* A code is accepted once: `gui_user_totp.last_step` holds the time step of the last code accepted, and an `UPDATE ... WHERE last_step < :step` whose row count is 1 decides, so the same code sent twice, or to two instances at once, works for one request. The code that confirmed the enrolment counts as used.
- *The secret at rest.* AES-256-GCM (`cryptography`, already locked for the OIDC ID tokens through `pyjwt[crypto]`; no dependency was added) under a key derived from `GUI_TOTP_KEY` with HKDF-SHA256 (one derivation per purpose, so the secret key and the recovery-hash key differ), a random 96-bit nonce per secret, and the user name as associated data, so a ciphertext copied into another user's row does not decrypt. The BFF cannot hash the secret (it needs it to compute codes), so what protects it is the key, which lives outside the database (`GUI_TOTP_KEY_FILE` from a mounted secret): a copy of the database or of a backup alone yields nothing usable. Without a key, enrolment is refused; with a different key than the one a secret was stored under, sign-in of that account fails closed (503 `TOTP_KEY_UNAVAILABLE`, an ERROR in the log naming the user, never a secret), and an admin resets the code.
- *Enrolment* (`/api/me/totp/begin`, `/confirm`): `begin` stores a new secret unconfirmed and returns the base32 secret and the `otpauth://` URI once; nothing signs in with it. `confirm` needs a valid code from it, then activates it and returns ten recovery codes. There is no QR image: the page shows the secret in groups for typing and the link for apps that open one (not taken: no QR rendering dependency). An OIDC user cannot enrol (the provider does it); an account that has a code cannot enrol another until an admin resets it.
- *Recovery codes.* Ten, each 16 characters of a 31-symbol alphabet without the look-alikes (about 79 bits), shown once at confirmation (and again only by making new ones, which replaces the old set and asks for a current one-time code). Stored as HMAC-SHA256 under a key derived from `GUI_TOTP_KEY`, over the user name and the code. Why not scrypt like the passwords: a slow hash protects a low-entropy secret that can be guessed offline, and a 79-bit random code cannot be, so a slow hash would only cost the CPU of every sign-in (ten comparisons); the key adds that a database copy cannot even be tested against guesses. A code is spent by an `UPDATE ... WHERE used_at IS NULL` whose row count decides, audited `RECOVERY_CODE_USED` with "n left", and the sign-in answer carries `recoveryCodesLeft` for the page to show.
- *The second step of a sign-in.* `POST /api/login` with a correct password for an account with a confirmed code creates no session and no cookie. It answers `{mfaRequired, challenge, expiresIn: 300}`: an HS256 token of kind `login-totp` carrying the user, the user's `token_version` and a random `jti`, signed with a key derived from the session key (so the challenge is never a valid session token, nor the other way round: tested), and backed by a `gui_login_challenge` row that makes it single use. `POST /api/login/totp` checks the signature, the kind, the five minutes, the row, that the user still exists, is active and has the same `token_version` (a password change or "revoke sessions" between the steps ends the sign-in), the lockout and the mode rules again, then the code; only the right code deletes the row and opens the session. A wrong code leaves the challenge usable (a typing slip should not cost the password) but is a failure in the same counter as a wrong password: five in all lock the account for five minutes (see Login lockout).
- *The password grant is not a way round.* `POST /api/token` for an account with a code needs the form field `otp` (a code or a recovery code); without it the grant is `invalid_grant`.
- *Break-glass (`PATCH ... {breakGlass: true}`).* A local account flagged by an admin signs in with password and one-time code even when the mode is `oidc`. It needs an enrolled code: without one 403 `BREAK_GLASS_NEEDS_TOTP` (so an admin sets the flag, enrols the code, and only then relies on it; the flag cannot be set on an `oidc:` user). Every break-glass sign-in, by cookie or by token grant, with a code or a recovery code, is audited `BREAK_GLASS_LOGIN` (not `LOGIN`) and logged at WARNING (`break-glass sign-in: <user> (role ...)`), in any mode. The step 2 re-checks the flag, so removing it between the steps stops the sign-in.
- *Admin MFA required (`GUI_ADMIN_MFA_REQUIRED`).* `current_session` refuses every route but `GET /api/me` and `/api/me/totp[/begin|/confirm]` with 403 `MFA_ENROLMENT_REQUIRED` for a local account of role admin that has no confirmed code (one read of `gui_user_totp` per request of such an admin, nothing for the others); `/api/me` says `mfaEnrolmentRequired: true`, and the SPA shows only Account security until it is done. A password-only session stays possible (the admin must be able to sign in to enrol), which is why it is a gate and not a refusal at login. The Bearer tokens of `/api/token` are gated the same way.
- *Admin actions.* `revoke-sessions` and `reset-totp` (section 2.4) are `require_admin` routes like the rest of `/api/admin`; the permission table `app/rbac.py` is the proxy's (`/api/smo/...`) and has no entry for the BFF's own routes, so the generated check for them is `tests/test_mfa.py::test_every_admin_route_is_admin_only`, which walks the app's routes under `/api/admin` and expects 401 without a session and 403 for viewer and operator, so a new admin route is covered the day it is added (the rbac matrix test, `tests/test_rbac_matrix.py`, stays as it was for the proxy table).
- *Not in the logs or the audit rows.* The secret, the codes, the recovery codes, the challenge and the key are never written: the audit `detail` says "one-time code" or "n left", never a value; `tests/test_mfa.py::test_no_secret_code_or_recovery_code_reaches_the_log_or_the_audit_trail` runs the flows at DEBUG and searches both.

**Not taken.** WebAuthn / FIDO2 security keys (a larger piece: relying-party id, attestation, a browser API; the TOTP layer is the baseline and WebAuthn can be added beside it); SMS or e-mail codes (a weaker factor than TOTP and a delivery dependency); a QR image (no rendering dependency; the setup key is typed); a "remember this device" bypass; self-service removal of the code (it would let a session thief remove the second factor; an admin resets it); a per-address rate limiter on the login routes (`SEC-8.6`); encrypting the secret with a key held by an external KMS (`SEC-4.5` is the place for that).

### 2.11 Signing keys (PR-SEC-5)

Off by default: with nothing set the session token is exactly what it was (HS256, `{"alg":"HS256","typ":"JWT"}`, no `kid`), a session issued by the release before keeps working across the upgrade, and `/.well-known/jwks.json` answers an empty key set.

**Turning it on.** Make a key pair, give the BFF the private key as a file, set the algorithm, restart:

```bash
openssl genpkey -algorithm EC -pkeyopt ec_paramgen_curve:P-256 -out private-key.pem     # ES256; for RS256: openssl genpkey -algorithm RSA -pkeyopt rsa_keygen_bits:3072 -out private-key.pem
# GUI_JWT_ALGORITHM=ES256  GUI_JWT_PRIVATE_KEY_FILE=/run/secrets/gui-jwt/private-key.pem
```

Compose reads both from the shell or `.env` and needs the file mounted by an override (as for `GUI_TOTP_KEY_FILE`); the chart takes `gui.jwtKeySecretRef` (a Secret of your own) and `gui.env.GUI_JWT_ALGORITHM` (`deploy/helm/smo/README.md`). The start is refused, naming the variable and never the key, for: an unknown algorithm; RS256 / ES256 without the key file; a key file with HS256 (it would be silently unused); an unreadable, encrypted or malformed key; the wrong key type (RSA for ES256, EC for RS256), an RSA key under 2048 bits, an EC curve other than P-256.

**What a token looks like, and what is refused.** Header `{"alg": "RS256" | "ES256", "typ": "JWT", "kid": <RFC 7638 thumbprint of the public key>}`, the same claims as before (`sub`, `ver`, `csrf`, `jti`, `iat`, `exp`). The verifier takes a token only when its header `alg` is exactly the configured algorithm, its `kid` names a key of the set, the signature verifies and `exp` is an integer in the future. So refused, each with a test: `alg: none`; an HS256 token signed with the public key (PEM, DER or stripped) as if it were the secret (algorithm confusion); a token of the other asymmetric algorithm; no `kid`, an unknown or non-string `kid`; the right `kid` signed by another key; a token that carries its own `jwk` / `jku` (ignored: the key never comes from the token); a stripped signature; an expired token or one without an integer `exp`. Everything after the signature (the revocation list by `jti`, `ver`, role read from the table, CSRF) is the code it was.

**Rotation.** (1) Make a new key pair. (2) Set `GUI_JWT_PRIVATE_KEY_FILE` to the new private key and list the old key's file (the public key is enough) in `GUI_JWT_PREVIOUS_KEY_FILES`; restart every instance. New sessions are signed with the new key and carry its `kid`; a session signed with the old one still verifies, matched by its `kid`, and the old public key is in the key set. (3) After `GUI_SESSION_TTL_SECONDS` (8 h by default) no old session is left: remove the old file from `GUI_JWT_PREVIOUS_KEY_FILES`. Removing it earlier ends the sessions that still carry it. A previous key never signs, even if the file is a private key. To end all sessions at once (a key was exposed), change the key and list no previous one. With several replicas, roll them all to the same key set: during the roll a token signed by an updated replica is refused by one that has not yet got the new key listed, so list the new public key first if sessions must not drop (the key set is read at start).

**Switching the algorithm ends every session, by design.** An HS256 session is refused by an RS256 / ES256 BFF and the other way round, and so is a session of another asymmetric algorithm; people sign in again. Accepting old HS256 tokens beside the new keys would have been possible (the BFF still holds `GUI_JWT_SECRET`), but then the shared secret stays a live way to forge a session, which is what moving to a key pair is meant to end; the cost of refusing them is one sign-in, at most `GUI_SESSION_TTL_SECONDS` old. Test: `test_switching_from_hs256_to_a_key_pair_ends_existing_sessions_and_a_new_login_works`.

**`GUI_JWT_SECRET` stays.** The login challenge of the one-time-code step (section 2.10) is an HS256 token under a key derived from it, and never leaves the BFF; it is not a session whatever the session algorithm is (tested). Without `GUI_JWT_SECRET` the generated key in `gui_setting` is used for that as before.

**The key set route.** `GET /.well-known/jwks.json`, section 2.4: public by design, public members only (`kty`, `use`, `alg`, `kid`, and `n`, `e` or `crv`, `x`, `y`), the secret of HS256 never. Nothing in this build fetches it: the BFF verifies its own tokens from its configured keys. It is there for a service that wants to verify a session token without holding a secret (a gateway, a log pipeline), and it is cacheable for five minutes, so a rotation reaches such a verifier within that time plus its own cache.

*Not taken.* A key generated and stored in the database (HS256 has `gui_setting`; for a key pair that would put a private key in a SQLite file the backup copies); an inline PEM in an environment variable (the file form only); an encrypted PEM with a passphrase (the passphrase would need a place of its own); EdDSA, RS384 / RS512, ES384 / ES512 (one RSA and one EC choice are enough; adding one is a line in `signing.py`); `x5c` / `x5t` in the key set; the BFF fetching its own key set; automatic rotation (a scheduled key change); a per-key algorithm in one key set (one algorithm per BFF, so a change of algorithm is a clean cut); `kid` and key rotation for the HS256 secret (a shared secret has no public half to publish, so it stays "change it and everyone signs in again", `docs/SECRETS.md`).
